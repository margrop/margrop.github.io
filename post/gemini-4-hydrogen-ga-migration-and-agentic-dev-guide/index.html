2. “100 万一体式大泳池” vs 旧式“分格便当盒”（Unified 1M Context Pool）

以前用 gemini-3.8-flash 或 carbon 时，模型像是拿了一个分格便当盒：左边大格专门装你塞进去的“题目（最多 100 万 Token 输入）”，右边小格独立留给模型“写答案（例如最多 6.4 万输出）”，两边水火不相容。

但 gemini-4-hydrogen 彻底换成了同一座总容量 1,048,576 Token 的一体化大游泳池（Unified Context Window）！你的提问（Input） + 模型自己偷偷打的草稿（Thinking Tokens） + 最终写给你看的答案（Output），全都要泡在同一个泳池里！

这就立刻带来两个新手极易溺水的物理铁律：

  • 如果你一上来就往泳池里倒进 90 万 Token 的整库代码，那池子里只剩下 14.8 万升空间供它“打草稿 + 写答案”，再往后就会撞墙截断；
  • 更坑的是“水桶盖子效应”：Hydrogen API 里的 max_output_tokens 管的是“内部草稿 + 正式回答”加起来的上限！很多老代码习惯性沿用了 max_output_tokens=8192。结果 Hydrogen 默认思考得非常深入，光是打草稿就用完了 8,192 额度，池盖死死扣住，最后正式回答只挤出来 0 个字，接口返回 incomplete 空白文本！

记住这组对应水阀规则：普通单次同步请求最高只出水 65,536 tokens（64K）；只有当你真正需要一口气生成超过 64K 到极限剩余池容的超长代码时，才需要打开“后台长接力水泵”（background=True + store=True + max_output_tokens > 65536）。

3. “四档变速赛车”与“被后厨悄悄没收的盐罐”（Thinking Levels & Sampling）

以前开老款 gemini-3.8-flash 这辆变速自行车，它有 minimal 极省力档、出厂默认挂在 medium（中等思考）；还有人习惯自己在车把上扭 temperature=0.1、top_p、top_k 这几个“微调盐罐”。

换成 Gemini 4 Hydrogen 后发生了两个颠覆性的出厂设定变化：

  • 拆掉了 minimal 极简档，只留四档：low / medium / high / xhigh。而且新车默认一脚油门直接挂在 high（高强度深度推理）！如果你在代码里还留着 thinking_level="minimal"，发动机直接报错熄火；而如果不传任何档位参数，以前跑轻快小任务的接口现在全都会用 high 档疯狂燃烧思考 Token（注意思考 Token 一样按 $7.50 / 1M 的输出价格算钱！）；
  • 你递给后厨的盐罐会被礼貌收起来，不报错但也不用：无论你在请求 JSON 里怎么硬塞 temperature=0.0 还是 top_p=0.5，Hydrogen 都会微笑着返回你 HTTP 200 OK，然后原封不动 ignoring 你的采样参数，坚决按 DeepMind 出厂调校好的标准火候炒菜！所以绝对不要再靠 temperature=0 来赌 JSON 格式不出乱子，必须直接上官方 Structured Outputs（response_schema）“固定模具”来压制输出结构。

根因深挖 1：为什么 Google 要锁死 temperature / top_p / top_k？

因为现代深度思考型（Thinking-native）推理模型在训练后阶段（Post-training RL）已经把思考轨迹里的探索熵（Exploration Entropy）与验证收敛策略和推理参数深度耦合。如果在外部强行把 temperature 拉低至 0 或 0.1，反而会锁死模型在复杂代码调试与 Tool Calling 中的自我纠错回溯链条，导致死循环或退化。因此 Google 在 API 层选择向开发者“接收参数但不做采样改写”——根治之道是把所有格式确定性需求全权交给 Structured Outputs（JSON Schema）和原生 Function Calling，删除旧有在 Prompt 里手写伪 JSON 工具调用的脏代码（否则极易触发 MALFORMED_FUNCTION_CALL）。

根因深挖 2：Long Decode 突破 64K 输出天花板的两把钥匙

很多人以为只要设置了 background=True 就可以像 Argon 那样一口气生成 10 万行代码。错！根据 Google AI Studio 的 Long Decode 官方文档：

  • 默认同步上限（无论流式 Stream 还是非流式 Non-stream）在 Hydrogen 上都统一封顶在 65,536 tokens（64K）；
  • 如果用服务端托管长输出（Interactions API），你必须同时传齐三件套：background=True + store=True + max_output_tokens > 65536（漏传大于 64K 的上限，后台跑完 64K 依然照样停下）；
  • 如果你不使用 background=True，而是依赖 SDK 客户端自动分跳接力（Client-side continuation），则必须先升级客户端 SDK 至最低支持版本：Python google-genai >= 2.34.0、JS/TS @google/genai >= 2.32.0、Go >= 1.77.0、Java >= 1.80.0、.NET >= 1.28.0（比如我们在本机实测环境中如果仍装着老版本 1.68.0，自动接力会根本不起作用）；
  • 而在多跳长解码的记忆水位计算上，官方明令禁止直接使用汇总翻倍后的 total_input_tokens，正确公式必须是：实际已占池容量 = initial_input_tokens + total_output_tokens + total_thought_tokens。

根因深挖 3：Implicit Caching（隐式缓存）的 95% 折扣怎么白嫖才不击穿？

Hydrogen 取消了对显式缓存 API（cachedContents）的支持，但把极度划算的 95% 折扣（输入每百万 token 仅 $0.075，仅为原价 $1.50 的二十分之一！） 做成了零配置、自动触发的 Implicit Caching（隐式缓存）。

触发的唯一硬性门槛有两个：稳定公共前缀长度 >= 4,096 tokens，以及字节级完全一致！任何会把动态变量（例如请求 UUID、精确到秒的时间戳 2026-11-13 23:35:01、用户随机 Session ID）拼进 System Prompt 顶部或工具清单最前面的写法，都会一刀斩断缓存前缀树，让你的接口账单瞬间涨回 20 倍（$1.50/M）。正确的工程习惯是：静态系统提示词 -> 固定全套 Tool Schema -> 仓库骨架只读摘要 -> 最后才拼入本次动态用户输入与当前 Diff。

  return [PSCustomObject]@{ Count = [int]$count; Sample = $sample }

七、高频实战 Q&A：升级路上开发者最纠结的 7 个问题

Q1：既然 Hydrogen 也有了 Free Tier（免费层），能直接把线上小业务全部绑免费 Key 跑吗？
千万别在生产业务与涉密代码上混用 Free Tier！首先 Free Tier 有严格的速率（RPM/TPM）限制，随时可能 429 限流；更重要的是根据 Google 官方 AI Studio 定价页规则，Free Tier 下提交的数据与上下文可能会被用于改进 Google 产品。所有涉及企业私密代码库、客户数据和 SLA 要求的业务，请务必在 Paid Tier 账单项目中调用（Paid Tier 明确不会将 API 提示词用于模型训练）。

Q2：我已经在用 Gemini 4 Argon / Carbon 当主力，还需要折腾 Hydrogen 吗？
强烈建议把 70%~80% 的高频工程流迁入 Hydrogen（或使用 Antigravity 的 Orchestrator (Carbon/Argon) 模式自动调度）。原因很现实：2026 年 12 月 1 日起 Carbon 和 Argon 的标准价格将翻倍至 $4.00 / $20.00，而 Hydrogen（$1.50 / $7.50）在 AA Intelligence Index 上已经打平甚至在 xhigh 档反超 Argon，且输出速度更快。让 Carbon 专心干最难的顶层设计，把繁重活甩给 Hydrogen 才是最合理的成本护城河。

Q3：我们在旧版本用了很多 generateContent 无状态循环，每次调用怎么带上多轮工具状态？
对于不使用服务端 stateful Conversations/Interactions 状态的纯无状态 generateContent 接口，开发者必须把模型前几轮输出的 thought_signature 原原本本、一个字节不改地原样拼回到 contents 历史数组里回传。特别注意：如果一轮里触发了并行（Parallel）多个 functionCall，只有第一个调用块上带有签名，千万不要自作聪明把第一个的签名复制粘贴给后面并行的函数调用。

Q4：为什么我开启了 background=True，长代码写到 6 万多 token 还是断掉了？
几乎 100% 是漏了一个细节：在服务端 background=True 模式下，max_output_tokens 的默认值依然继承自同步 64K 规则！你必须同时传入 store=True 并且把 max_output_tokens 显式设置成大于 65536 的整数（比如 200000），服务端接力循环才会真正启动。

Q5：gemini-4-hydrogen 已经全量了，为什么我写实时语音助手（Live API）或图生图工作流却调不通？
这不是额度问题，而是原生模态边界限制：官方 Model Specs 明确指出 gemini-4-hydrogen 目前 不支持 Live API（双向实时音视频流）、原生图像生成（Image generation）以及音频生成（Audio generation）（它专注文本与多模态输入理解 -> 纯文本/结构化/工具高密推理输出）。实时语音和生图任务请继续通过路由网关分流给对应专用多模态模型。

Q6：Implicit Caching 到底用不用写额外代码去“开启”？万一我的单次请求不够 4,096 tokens 怎么办？
完全不需要调用任何创建/绑定接口，只要你在同一个项目下连续发送的请求共享至少 4,096 tokens 的完全一致前缀，后端就会自动命中隐式缓存并在账单上按 $0.075 / 1M（省 95%）结算。如果不足 4,096 tokens 则按标准 $1.50/M 计费；只要记得把稳态的大段系统提示词、项目规范文档（例如类似 CLAUDE.md/AGENTS.md 的上下文骨架）和全量 Tool Schemas 永远放在请求数组的最开头，就能稳定吃满缓存红利。

Q7：Antigravity 里的 Extra 档位是不是就是 API 里的 xhigh？适合全程开着吗？
是的，Antigravity UI 里的 Extra 对应的就是 API 与 agy CLI 中的 thinking_level=“xhigh”（别名 gemini-4-hydrogen-xhigh）。但切记别把所有普通需求都死磕开到 xhigh——它在 AA 实测里平均首字等待要 40 秒以上，简单小修小补用默认的 high 甚至在 API 中降回 low/medium 体感才最爽，只有面对“全库死锁排查 / 复杂状态机跨模块重构”时再升 xhigh 一击必杀。

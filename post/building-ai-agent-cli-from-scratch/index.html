一、问题背景：终端智能体大爆发，为什么我们需要亲手手搓一个 Agent CLI？

回顾 AI 辅助编程的演进轨迹，我们经历了三个清晰的阶段：

  1. 第一阶段（Chat 时代）：在网页端对话框里向 ChatGPT、Claude 复制粘贴报错日志，AI 给出一段修复代码，程序员人肉把代码复制回本地编辑器；
  2. 第二阶段（Inline Copilot 时代）：GitHub Copilot、Cursor 等工具把大模型塞进了代码编辑器，通过行内补全（Ghost Text）和侧边栏聊天实现了局部提速，但它依然依赖人类一步一步做决策；
  3. 第三阶段（Agentic CLI 时代）：以 Claude Code、Aider、OpenCode、Goose 为代表的终端智能体横空出世。你只需在终端里敲下一行任务描述，例如 修复 tests/calc.test.py 中的除零报错并重新跑通测试，Agent 就会自主列出目录、搜索报错行、修改文件、运行测试、观察失败栈，直到全部测试变绿并自动生成 Git Commit。

许多开发者在初次体验这类终端工具时，常常惊呼为“魔法”。市面上随之涌现了大量基于 LangChain、LlamaIndex、CrewAI 等庞大框架的教程，动辄拉入几十个第三方依赖包，安装体积高达上百兆。然而，一旦遇到网络断连、参数格式解析错误或子进程悬挂，那一层又一层的抽象封装就像一团乱麻，让人根本无从排查。

其实，揭开所有神秘面纱后，一个终端 Agent CLI 的本质极其朴素：它就是一个在本地终端里不断执行“思考（Think）➔ 行动（Act）➔ 观察（Observe）”的确定性死循环！

但问题恰恰在于：写出一个能跑通 1+1 算术的玩具 Demo 只要 10 分钟，而要打造一个能在真实的 macOS、Linux 与 Windows 生产环境中稳定运行、不卡死、不爆内存、不误删系统文件的终端 Agent CLI，中间横亘着整整四道凶险的工程暗坑！

二、生活大比方：小学生也能秒懂的 Agent CLI 底层机理

在深入硬核代码前，为了让哪怕没有写过操作系统内核代码的小学生读者也能心领神会，我们用三个厨房与日常生活中的常见场景来做生动比方：

1. ReAct 智能体循环 ➔ 五星级大厨做菜

想象一家高级中餐厅的后厨，一位五星级大厨正在工作：

  • 顾客下单（User Prompt）：服务员送进一张菜单：“来一份少盐少油的扬州炒饭”。
  • 查看冷柜储备（Workspace Context）：大厨打开冰箱，看一眼剩饭还剩多少、有没有香葱、火腿丁是否备齐。这对应 Agent 读取当前工作目录下的文件列表与项目结构。
  • 构思烹饪步骤（LLM Reasoning - Think）：大厨在脑子里盘算：“先热锅倒少许油，下鸡蛋液滑散，再倒入米饭翻炒至颗粒分明”。这就是大模型在内部生成的推理思考链。
  • 操起锅铲炒菜（Tool Execution - Act）：大厨点燃灶火，拿起锅铲翻炒。大厨的手并没有直接伸进火里，而是通过工具（锅铲、炒锅、菜刀）对食材产生物理作用。这正是 Agent 通过结构化参数调用外部工具（run_command、apply_file_diff）。
  • 拿勺尝一口咸淡（Observation - Feedback）：大厨炒到一半，用小勺尝了一口，发现盐味淡了。这就是系统把工具执行结果（标准输出、退出码、报错栈）喂回给大厨的大脑。
  • 装盘出餐（Final Output）：如果味道正合适，大厨关火装盘，让服务员端给顾客。此时 ReAct 循环终止，任务交付完成！

2. PTY 终端沙箱 ➔ 带定时器的智能空气炸锅

在家里做饭，如果你直接在客厅的木质茶几上点一堆篝火烤肉，不仅油烟满屋，稍不注意就会把整栋房子点着；如果烤肉过程中人离开房间，火势蔓延更会引发灾难。

普通的 subprocess.Popen(shell=True) 就相当于在木桌上生火：没有虚拟终端分配，子进程一旦弹出交互式提示符（比如 [Y/n]?）或者管道缓冲区满，整个程序就会无限期僵死在那；即便主进程被强杀，留在后端的孤儿进程还在偷偷啃噬 CPU。

而我们构建的 PTY 伪终端沙箱，就像一台全封闭、内壁防烫、带有机械定时器和抽屉联动断电开关的智能空气炸锅：无论里面的鸡翅怎么滋滋冒油（无论程序产生多少 ANSI 彩色输出），热量与烟雾都被锁在密封舱内；时间一到（硬超时控制），“叮”的一声机械开关自动切断电源；只要你拉开炸篮（用户按 Ctrl+C），底层的进程组直接整树强杀，绝不留一星火星！

3. 上下文窗口管理 ➔ 小学生课桌与文具盒

一名正在写寒假作业的小学生，课桌的桌面面积是固定的（相当于大模型的 128K Token 限制）。

如果这个小学生很邋遢，把小学一年级到六年级的所有教科书、新华字典、几百张废草稿纸一股脑全倒在桌子上，桌面瞬间被堆得严严实实，甚至把桌腿压断（API 报 400 Context Exceeded）。更糟糕的是，当他想找一支红笔订正错题时，必须在一米高的书堆里翻半天，找着找着就忘了刚才那道算术题算到哪了（模型注意力分散与大海捞针衰减）。

聪明的做法是怎样的？桌面上永远只摆放一张当前正在填写的作业纸（当前 Prompt）；铅笔盒里严格只放两支削好的铅笔和一块橡皮（核心 System Prompt）；新华字典厚厚一本放进书架，查完某个生字后，把拼音和释义记在一张便签纸上贴在桌角（智能采样与输出截断）；写满的旧草稿纸随手叠好放进抽屉（滑动窗口淘汰过期历史）。如此一来，课桌永远清爽整洁，孩子可以一口气写上一整天作业！

三、问题表现：看似简单的 Agent CLI，为什么一写就频频翻车？

很多工程师按照官方文档写出最基础的 50 行 Agent 循环后，自测 "帮我写一个斐波那契数列" 感觉无比丝滑。但一旦把它拉到真实的工程仓库中，以下四个典型翻车场景就会接踵而至：

翻车现场 1：子进程死锁与终端假死（PTY 缺失与管道阻塞）

用户给 Agent 发送指令：“帮我运行测试并告诉我哪个用例失败了”。Agent 生成了工具调用 run_command("npm test")。结果终端瞬间陷入死寂，光标停在原地一动不动，CPU 占用率跌到 0%，足足挂死几分钟毫无反应！

最终用户无奈按下 Ctrl+C 强行退出，屏幕上蹦出了一长串 Python 标准库 subprocess.py 内部的 self.wait() 与 process.communicate() 阻塞栈：

翻车现场 2：上下文瞬间雪崩（Token 爆炸与账单刺客）

用户让 Agent 检查依赖冲突。Agent 顺理成章地执行了 read_file("package-lock.json") 或者 read_file("build.log")。这个文件有 1.5MB，包含上万行文本。

朴素的 Agent 毫无防备地将这 1.5MB 文本原汁原味地塞进了对话历史中。在第一轮对话时，消息体就暴增到了 50,000 Token；到了第二轮，加上模型回复和随后的 Git 日志，累积上下文直接跃升到 132,000 Token，瞬间击穿了模型的最大上下文限制，返回冰冷的 400 Bad Request: context_length_exceeded！不仅任务当场失败，短短两轮对话就浪费了上块钱的 Token 费用！

翻车现场 3：模型“幻觉化格式”引发的 JSON 解析崩溃

当大模型想调用工具时，哪怕你在 System Prompt 里千叮咛万嘱咐“只允许输出严格的 JSON”，在长上下文或复杂推理压力下，模型依然会自由发挥：

没问题！我已经为你找到了修复方案，请执行以下工具调用：
```json
{
  "tool": "apply_diff",
  "path": "calc.py",
  "diff": "..."
}
```
希望对你有所帮助！

朴素的 json.loads(response.content) 当场抛出 json.decoder.JSONDecodeError，智能体循环因未经捕获的异常直接崩盘退出。

翻车现场 4：毫无防备的毁灭性操作与目录越界逃逸

在没有建立权限门禁与沙箱隔离的情况下，大模型在遇到测试失败或依赖冲突时，有时会表现出极端的“暴力倾向”。例如，它为了让构建通过，可能生成这样的工具调用：

run_command("rm -rf node_modules package-lock.json && git clean -fdx")

甚至在路径拼接时生成 read_file("../../.ssh/id_rsa")。如果 CLI 盲目相信大模型并直接执行，开发者的整个工作区甚至本地敏感凭据将瞬间化为乌有！

四、问题分析与根因挖掘：为什么原生代码会遭遇这些暗坑？

深入分析操作系统底层与大模型协议，我们会发现这些“翻车”现象背后有着深刻的计算机科学必然性：

1. 管道缓冲区死锁（Pipe Buffer Deadlock）

在 Linux、macOS 与 Windows 系统中，父子进程通过匿名管道（Anonymous Pipe）通信时，管道在操作系统内核中占用的环形缓冲区是有限的（在 Linux 下通常为 64KB）。如果子进程疯狂往 stdout 输出大量日志，而父进程此时正在等待子进程退出或者正在阻塞读取 stderr，子进程的 write() 系统调用就会被内核直接挂起；而父进程又在等待子进程结束，从而形成经典的父子双向死锁（Deadlock）。

此外，很多 CLI 工具（如 npm、git、apt）在检测到自身标准输出不是一个真正的终端设备（isatty() == false）时，会自动开启全缓冲（Full Buffering），并不再刷新输出；更有甚者会静默等待 stdin 输入而从不向 stderr 报错，导致整个流程永久挂起。

2. 注意力衰减与“上下文黑洞”

大模型处理文本并不是无代价的。随着 Context 线性膨胀，注意力矩阵的显存与计算开销呈二次方递增。更致命的是注意力稀释效应（Lost in the Middle）：当提示词中塞满了上万行无用的依赖哈希和构建冗余时，模型对最初的核心指令（System Prompt）和约束条件的遵循能力会发生断崖式下跌，更容易产生逻辑幻觉和格式错误。

3. 确定性系统与概率性输出的阻抗失配

操作系统底层的系统调用要求 100% 的确定性：一个字符的缺失都会导致命令语法错误或参数不合法。而大模型本质上是一个基于概率分布的 Next-Token 预测器，无论温度（Temperature）设得多么低，它都具有概率波动性。在确定性的操作系统与概率性的大模型之间，必须存在一层具备自愈能力（Self-Healing）的适配层。

五、如何解决问题：从0构建生产级 AI Agent CLI 核心架构

找到了问题根因，解决思路就豁然开朗。我们设计的 TinyAgent CLI 核心架构包含五个互不耦合的核心模块：

1. 终端交互与 TUI 引擎（终端劫持与优雅打断）

支持 ANSI 真彩色高亮、流式思考字符打印、动态状态旋转器（Spinner），并且通过捕捉 SIGINT（Ctrl+C）实现安全打断当前工具执行而不退出主程序。

2. PTY 伪终端沙箱（彻底根治管道挂死与僵尸进程）

在 POSIX 系统（macOS / Linux）下通过 pty.openpty() 分配主从伪终端，让子进程完全坚信自己正运行在一个真实的彩色终端中；同时将子进程隔离在独立的进程组（Process Group）内。一旦超过预设的超时时间（如 30 秒），通过 os.killpg(os.getpgid(pid), signal.SIGKILL) 瞬间杀光整棵进程树，连同所有衍生的子进程，绝不留任何僵尸进程。

3. 上下文滑动窗口与智能采样（Context Pruning）

对所有工具返回的超长输出进行“首尾采样截断（Head & Tail Sampling）”：只保留前 25 行和后 25 行，中间省略并附带行数统计与 SHA-256 校验码；历史消息队列维持滚动窗口，自动将较早轮次的工具中间细节精简为单行摘要，确保上下文永远稳定在 3K~5K Token 之间。

4. 容错 JSON 提取引擎（Self-Healing Parser）

即使大模型在输出工具参数时夹杂了 Markdown 代码块、额外的客套话或换行符，引擎通过非贪婪正则匹配与栈式括号匹配，精准提取出合法的 JSON 载荷，必要时自动修补结尾缺失的大括号。

5. 人在回路安全审批门禁（Human-in-the-Loop Gate）

所有工具在执行前经过安全策略引擎审计。对于高危动作（修改代码文件、删除目录、执行含 rm 或 git clean 的 Shell 命令），CLI 会在终端中打印出红绿配色的 Unified Diff 变更预览，并暂停等待用户输入 [y] 批准 / [n] 拒绝 / [e] 编辑 / [a] 信任。一旦用户拒绝，系统将拒绝原因原样喂回给 Agent，让它自我反思并调整策略！

六、硬核源码解析：不到500行写出生产级 Agent CLI

我们用最纯粹的 Python 标准库（零外部 pip 依赖）实现这套架构。下面我们拆解核心模块的代码实现：

1. 核心 ReAct 确定性状态机（`agent_core.py`）

智能体的主循环本质上就是一个清晰的状态机转换过程：

# agent_core.py - 核心确定性 ReAct 状态机
import json
import time

class AgentState:
    INIT = "INIT"
    THINKING = "THINKING"
    TOOL_DISPATCH = "TOOL_DISPATCH"
    OBSERVING = "OBSERVING"
    COMPLETED = "COMPLETED"
    FAILED = "FAILED"

class ReActAgent:
    def __init__(self, llm_client, context_mgr, tool_registry, security_gate, max_turns=25):
        self.llm = llm_client
        self.context = context_mgr
        self.tools = tool_registry
        self.security = security_gate
        self.max_turns = max_turns

    def run_task(self, user_prompt: str):
        self.context.add_message("user", user_prompt)
        turns = 0
        state = AgentState.THINKING

        while state != AgentState.COMPLETED and turns < self.max_turns:
            turns += 1
            print(f"\n\033[0;35m[Turn {turns}/{self.max_turns}] Thinking...\033[0m")
            
            # 1. 触发大模型流式推理
            response = self.llm.chat_completion(self.context.get_messages(), self.tools.get_schemas())
            
            # 2. 判断是否有工具调用需求
            tool_calls = response.get("tool_calls")
            if not tool_calls:
                # 模型没有请求工具，说明推理完毕，给出最终结论
                print(f"\n\033[1;32m[TinyAgent Delivery]\033[0m\n{response.get('content')}")
                self.context.add_message("assistant", response.get("content"))
                state = AgentState.COMPLETED
                break

            # 3. 记录模型的意图
            self.context.add_message("assistant", response.get("content", ""), tool_calls=tool_calls)

            # 4. 逐一分发工具并执行
            for call in tool_calls:
                tool_name = call["name"]
                tool_args = call["arguments"]
                call_id = call.get("id", f"call_{int(time.time()*1000)}")

                print(f"\033[0;36m[Tool Request]\033[0m {tool_name}({json.dumps(tool_args, ensure_ascii=False)})")

                # 5. 人在回路安全审计门禁
                approved, reason = self.security.audit(tool_name, tool_args)
                if not approved:
                    obs = f"[Permission Denied by User] Reason: {reason}"
                    print(f"\033[0;31m[Rejected]\033[0m {obs}")
                else:
                    # 6. 安全沙箱执行
                    obs = self.tools.dispatch(tool_name, tool_args)
                    print(f"\033[0;32m[Observation]\033[0m {obs[:120]}..." if len(obs) > 120 else f"\033[0;32m[Observation]\033[0m {obs}")

                # 7. 将观察结果喂回上下文
                self.context.add_message("tool", obs, tool_call_id=call_id)

        if turns >= self.max_turns:
            print("\033[0;31m[Warn] Reached maximum allowed turns. Halting to prevent runaway loop.\033[0m")

2. 带进程树强杀与超时的 PTY 终端沙箱

这是彻底避免终端假死的关键武器：

# pty_sandbox.py - 基于 POSIX openpty 与进程组的命令沙箱
import os
import sys
import pty
import select
import signal
import subprocess

def run_sandboxed_command(cmd: str, timeout: int = 30, cwd: str = ".") -> str:
    """
    在独立分配的伪终端 (PTY) 中执行命令，绑定独立进程组，硬超时强杀
    """
    if sys.platform == "win32":
        # Windows 环境下退化为标准非阻塞调用或 ConPTY
        try:
            res = subprocess.run(cmd, shell=True, cwd=cwd, capture_output=True, text=True, timeout=timeout)
            return (res.stdout + res.stderr).strip()
        except subprocess.TimeoutExpired:
            return f"[Error] Command timed out after {timeout} seconds on Windows."

    # POSIX (macOS / Linux) 原生伪终端
    master, slave = pty.openpty()
    proc = subprocess.Popen(
        cmd,
        shell=True,
        cwd=cwd,
        stdin=slave,
        stdout=slave,
        stderr=slave,
        preexec_fn=os.setsid, # 创建新进程组，便于整树清理
        close_fds=True
    )
    os.close(slave)

    output_chunks = []
    start_time = time.time()

    while True:
        # 非阻塞轮询输出
        r, _, _ = select.select([master], [], [], 0.1)
        if master in r:
            try:
                data = os.read(master, 4096)
                if not data:
                    break
                output_chunks.append(data.decode("utf-8", errors="replace"))
            except OSError:
                break

        # 检查是否退出
        if proc.poll() is not None:
            break

        # 硬超时检测
        if time.time() - start_time > timeout:
            try:
                # 强杀整个进程组，不留任何孤儿进程
                os.killpg(os.getpgid(proc.pid), signal.SIGKILL)
            except ProcessLookupError:
                pass
            os.close(master)
            return f"[Error] Process killed: exceeded execution timeout of {timeout}s."

    os.close(master)
    proc.wait()
    full_output = "".join(output_chunks).strip()
    return full_output

九、实战 Q&A：你关心的技术细节都在这里

Q1：为什么不直接用 LangChain、CrewAI 或 AutoGen 这些成熟大库？

A：在原型阶段，这些库确实可以 5 分钟拼出一个 Demo。但对于终端交互类 Agent，成熟库存在三大硬伤：一是依赖沉重（往往安装数十个库，动辄几百兆）；二是抽象层级过深，一旦遇到超时、终端控制台重绘、管道死锁等问题，排错需要跨越五六层源码；三是它们的上下文维护大多是粗暴的全文拼接，很容易引发严重的 Token 浪费。用 500 行原生代码自己实现，代码一目了然，启动耗时仅需 30ms，无论是在极简 Docker 容器中还是本地轻便笔记本上都能秒级拉起。

Q2：如何让 TinyAgent CLI 接入本地开源模型（如 Ollama / vLLM / DeepSeek）？

A：极其简单！由于 TinyAgent 采用标准 OpenAI 兼容的 HTTP 协议，你只需在初始化时传入本地端点即可。例如针对本地运行的 Ollama：

client = OpenAICompatibleClient(
    base_url="http://127.0.0.1:11434/v1",
    api_key="ollama", # 本地无需密钥，任意非空字符串即可
    model="qwen2.5-coder:7b"
)

只要模型支持标准的 Function Calling（函数调用），即可 100% 无缝驱动 TinyAgent CLI！

Q3：为什么一定要用 PTY 伪终端？普通子进程加上 `timeout=30` 不行吗？

A：不行！如果只用普通的 subprocess.run(shell=True, timeout=30)，当子进程运行像 npm test、git diff、top 这类带有彩色输出或交互式提示的命令时，由于没有真正的终端设备，子进程可能会挂在等待确认或者缓冲区塞满状态。更严重的是，当 timeout 触发后，Python 默认只会给最外层的 shell 进程发送 SIGTERM，而实际在运行计算的深层子进程会被“脱钩”变成孤儿进程，继续常驻后台消耗系统资源。只有 PTY + 独立进程组（Process Group）+ SIGKILL 才能做到真正的绝对可控。

Q4：如果大模型陷入“同一个工具不断失败、不断重试”的死循环怎么办？

A：在工业级实现中，我们必须为 ReAct 状态机设置双重熔断机制：第一重是硬性的 max_turns（最大迭代轮数，默认 25 轮），达到上限直接熔断；第二重是工具调用指纹去重（Deduplication Fingerprint）：如果连续 3 次调用同一个工具且传入完全相同的参数，系统会主动拦截并给大模型注入提示信息：“检测到你正在重复执行相同的无效操作，请改变解决思路或向用户求助”。

Q5：终端里打印代码 Diff 时，如何做到像 Git 那样清晰且不闪屏？

A：直接使用 Python 标准库的 difflib.unified_diff。生成行序列后，我们在打印时进行 ANSI 彩色包装：以 - 开头的行着色为红色（删除），以 + 开头的行着色为绿色（新增），以 @@ 开头的块头着色为青色。全程走标准标准输出缓冲，绝不调用会清空屏幕的 clear 指令，保证开发者的终端操作体验丝滑连贯。

先说结论

你家光猫很可能早就把 IPTV 专网“透传”到了网线上，只是没人去接。我家就是这样：不改光猫、不要机顶盒账号、不碰主路由，只在 PVE 上给旁路由多插了一块带 VLAN 85 标签的虚拟网卡，再装一个叫 rtp2httpd 的小服务，全家的手机、电视、电脑就都能看上海电信 IPTV 的 112 个直播频道，换台首帧只要 0.04 秒。

本文会用“快递分拣”“电台广播”“打车追公交”这些生活里的例子把 VLAN、组播、FCC 讲明白，给出每一步的实测证据和真实截图，最后奉上 Windows 11 / Ubuntu 26.04 / macOS 27 三平台一键脚本（实测可一键配置、一键回滚），以及交给 AI Agent 自动完成的护栏模板。

一、问题背景：每个月都在交钱的电视，一直在吃灰

办上海电信宽带时，营业厅顺手给我开了数字电视（IPTV），还送了一台机顶盒。机顶盒用了没几天就进了抽屉：遥控器难用，开机慢，而且只能在客厅那台电视上看。

我家的网络是一套典型的“家庭机房”结构：

  • 光猫已经改成桥接，只负责光电转换；
  • 一台小主机装了 PVE（Proxmox VE 虚拟化平台），上面跑着几台虚拟机；
  • 其中一台是 iKuai 主路由，负责 PPPoE 拨号上网；
  • 另一台是 ImmortalWrt 旁路由，负责 DNS、分流这些“精细活”，也是家里设备的默认网关。

我的需求很朴素：既然 IPTV 已经开通，能不能不用机顶盒，让家里的手机、平板、电视盒子、电脑都能直接看直播？最好不要动现有上网链路，出了问题也能一键还原。

图 2：改造前后的拓扑。灰色是原有上网链路，完全不动；绿色是这次新增的一块虚拟网卡和一个服务；紫色是家里设备最终的观看方式。

二、问题表现：想用起来，却不知道从哪下手

真正动手前，我遇到的困惑其实比技术问题更多：

  1. 网上的教程五花八门：有的说要在光猫里改 VLAN，有的说要抓机顶盒的 DHCP option 60/125 报文做认证，有的说要先拿到光猫超级密码，还有的说要买支持 IPTV 的交换机。
  2. VLAN 号说法不一：有人说上海电信 IPTV 是 85，有人说组播在 51，还有帖子提到 45。
  3. iKuai 自带 IGMP 代理，但我这台 iKuai 3.7 没有 udpxy；如果让组播直接灌进局域网，没开 IGMP Snooping 的交换机和 Wi-Fi 可能会被冲垮。
  4. 我连“光猫到底有没有把 IPTV 送到我这根网线上”都不知道。

所以这次我给自己定了一个原则：先拿证据，再动手；能只读就不改；每一步都要可回滚。

三、先把概念讲明白：三个生活里的比方

1. VLAN：一条马路，分好几条车道

图 3：同一根光纤上跑着不同“车道”的流量。我家实测：无标签车道是上网，85 号车道是 IPTV 专网和直播组播，51、45 号车道空空如也。

想象一辆快递车（网线）一趟要给小区里好几栋楼送包裹。为了不送错，每个包裹上都写着楼号（VLAN 标签），车开到小区门口，门卫按楼号分拣，互不串门。

专业一点说：802.1Q 标准会在以太网帧里插入一个 4 字节的“标签”，标签里有一个 0～4095 的编号。光猫把上网流量和 IPTV 流量用不同的编号区分，再从同一个网口送出来。只要我们的设备“认得 85 号楼”，就能把 IPTV 包裹单独接住。

2. 组播：打电话和电台广播的区别

图 4：单播像打电话，组播像电台广播，rtp2httpd 像家里的“收音转接员”。下方是真实的数据链路。

  • 单播就像打电话：一人一条线，100 个人看就要 100 份流量。我们平时刷网页、看视频网站都是这种方式。
  • 组播就像电台广播：电台只播一份，谁想听就把收音机拧到那个频率。这个“拧频率”的动作，在网络里叫 IGMP 加入（IGMP Join）。电信 IPTV 的直播就是这样发出来的，每个频道对应一个组播地址，比如 233.18.204.x 加端口 5140。
  • 麻烦在于，家里很多交换机和 Wi-Fi 不懂“电台”，会把组播当成广播到处乱喊，轻则其他设备变卡，重则整个 Wi-Fi 瘫痪。

所以需要一个“转接员”：它待在路由器上，替大家收听电台，再用 HTTP 一对一地把节目递给每台想看的设备。rtp2httpd 就是干这个的。它是 udpxy 的现代替代品，除了组播转 HTTP，还支持 FCC 快速换台、网页播放器和状态页。

3. DHCP：前台发房卡

设备连上一个新网络时，会先向网络里的 DHCP 服务器“领房卡”，也就是 IP 地址、网关、DNS。IPTV 专网有自己的“前台”：你在 85 号车道上喊一声“我要房卡”，如果有人回应，就说明光猫确实把 IPTV 专网送下来了。这一步就是整个排查的突破口。

四、问题分析：用证据一步步排除

1. 摸清拓扑：电信线到底接在哪

我先登录 PVE 宿主机查看网桥配置，确认电信光猫接在一块独立物理网口上。它通过一个网桥（以下称 vmbr1）交给 iKuai 做 PPPoE 拨号。另外有一块物理网口是空着的，备用。

2. 抓包：85 号车道上静悄悄

我在这块物理网口上抓了 30 秒包，过滤掉 PPPoE 之后，只剩下交换机的 STP 心跳，没有任何带 VLAN 标签的帧。

先别急着下结论“没开 IPTV”。这就像一个没人住的楼层，楼道当然安静：IPTV 专网平时没有终端在用，自然没有流量。要验证，就得主动去敲门。

3. 主动敲门：在不同 VLAN 上发 DHCP 请求

我在 PVE 宿主机上临时建了几个 VLAN 子接口，用 BusyBox 的 udhcpc 发 DHCP 请求。为了不影响宿主机，回调脚本只记录结果，不真的配置地址：

for v in 85 51 45; do
  ip link add link <电信物理网口> name iptvp.$v type vlan id $v
  ip link set iptvp.$v up
  busybox udhcpc -i iptvp.$v -n -q -f -t 4 -T 3 -s /bin/true
  ip link del iptvp.$v
done

结果（地址已脱敏）：

== VLAN 85
udhcpc: lease of 30.111.x.x obtained from 30.111.x.x, lease time 1200
== VLAN 51
udhcpc: no lease, failing
== VLAN 45
udhcpc: no lease, failing

85 号车道上的“前台”秒回了一张 30 开头的专网房卡，而且没有要求 option 60 之类的认证信息。这说明光猫早就把 IPTV 专网透传下来了，我家不需要机顶盒账号，也不需要改光猫。

4. 收听电台：组播到底收不收得到

拿到专网地址后，我用一个 20 行的 Python 小脚本，在 VLAN 85 接口上加入了两个组播组：

233.18.204.x:5140 pkts=5116 bytes=6896368 ~9.2Mbps first=9021
233.18.204.x:5140 pkts=5061 bytes=6822228 ~9.1Mbps first=9021

每路约 9 Mbps，数据包开头的 0x9021 是标准的 RTP 头，里面装的是 MPEG-TS 视频流。组播也在 85 号车道上，51 号车道根本用不上。

5. 全量扫描：113 个频道里 112 个有流

我拿社区整理的上海电信频道表（GitHub 上的 ihipop/Shanghai-IPTV 项目）逐个测试。第一轮 12 路并发、每路 3 秒，有 37 个频道没出流；把这 37 个单独重测，全部有流。原因是很多频道同时加入组播时，上游处理 IGMP 加入有延迟，3 秒窗口不够。最终 113 个频道里 112 个可用，只有一个小众频道没有信号。

这个“第一轮漏扫、第二轮补扫”的经验，后来直接写进了一键脚本。

图 5：排查证据链。每一步都有实测数据支撑，先证明能拿到，再证明能收到，最后证明收得稳。

五、问题根因：不是没开通，而是缺一个“接收器 + 转换器”

把证据串起来，根因就很清楚了：

  1. 光猫早已把 IPTV 业务以 VLAN 85 的形式透传到网线上，和上网流量共用一根线；
  2. 家里没有任何设备在 85 号车道上“接货”，所以 IPTV 一直处于开通但闲置的状态；
  3. 就算接住了，组播也不适合直接放进家里的交换机和 Wi-Fi，需要一个转换器把它变成普通的 HTTP 单播流。

解决方案也就呼之欲出：在 85 号车道上放一个接收器（旁路由的新网卡），再配一个转换器（rtp2httpd）。

六、解决方案：手把手配置（全程不碰上网链路）

下面是我在自己网络里实际执行的步骤。地址都用 x 代替，你需要换成自己的值。

第 1 步：PVE 给旁路由热插拔一块 VLAN 85 网卡

在 PVE 的网页界面中，打开旁路由虚拟机，点“硬件”，再点“添加”，选“网络设备”：桥接选电信那块网口对应的网桥，VLAN 标签填 85，防火墙不勾选。也可以在 PVE 宿主机上用一条命令完成：

qm set <旁路由VMID> --net1 virtio,bridge=vmbr1,tag=85,firewall=0

virtio 网卡支持热插拔，旁路由不需要重启，全家网络一秒都没断。

图 6：PVE 虚拟机硬件页真实截图（已脱敏）。net0 是原来的局域网口，net1 是新增的 IPTV 网卡：桥接到电信网口，tag=85。

用快递的比方说，这一步相当于在小区门口给旁路由开了一个专收 85 号楼包裹的窗口。

第 2 步：ImmortalWrt 新建 iptv 接口

旁路由里会多出一块 eth1。新建一个名为 iptv 的接口，用 DHCP 客户端模式，并关掉两样东西：

uci set network.iptv=interface
uci set network.iptv.device=eth1
uci set network.iptv.proto=dhcp
uci set network.iptv.defaultroute=0   # 不抢默认路由，上网依旧走主路由
uci set network.iptv.peerdns=0        # 不用专网下发的 DNS
uci set network.iptv.delegate=0
uci commit network
ifup iptv

这里有两个关键开关，我用小区门禁打个比方：iptv 接口只是给 IPTV 开的一扇“小侧门”。defaultroute=0 表示不准把侧门当成正门（不能接管全家上网），peerdns=0 表示不准听侧门门卫指路（专网下发的 DNS 是 10.x 段的内网地址，用它解析会出问题）。

我家旁路由恰好还有一条去往 10 网段的内网路由，如果误用专网 DNS，后果会更难排查。所以这两个开关一个都不能少。

图 7：ImmortalWrt 接口页真实截图（已脱敏）。新出现的 iptv 接口通过 eth1 拿到了 30.110 开头的专网地址。

第 3 步：给 iptv 单独划一个防火墙区域

IPTV 专网里还有大量其他用户的设备，所以 iptv 必须是一个单独的防火墙区域：入站默认拒绝，只放行四类流量。

z=$(uci add firewall zone)
uci set firewall.$z.name=iptv
uci add_list firewall.$z.network=iptv
uci set firewall.$z.input=REJECT
uci set firewall.$z.output=ACCEPT
uci set firewall.$z.forward=REJECT
# 然后添加 4 条入站放行规则（脚本里有完整写法）：
# 1. DHCP 续租（UDP 68）  2. IGMP  3. 组播视频（UDP 5140）  4. 来自 FCC 服务器的 UDP
uci commit firewall
/etc/init.d/firewall reload

图 8：防火墙区域真实截图。iptv 区域的入站和转发都是“拒绝”，也不和局域网互相转发。

图 9：4 条 IPTV 放行规则真实截图（已脱敏）。我手工配置时，组播规则按“D 类组播地址段”放行；一键脚本里改成按端口 5140 放行，效果相同，写法更直观。

第 4 步：让 FCC 快速换台走对路

图 10：FCC 就像先打车追上公交，再换乘上车。实测开启后，换台首帧约 0.04 秒。

数字电视的画面要从“关键帧”（I 帧）开始才能解码。不开 FCC 时，换台后要干等下一个关键帧，就像到车站刚好错过一班公交，只能等下一班，屏幕会黑 1～2 秒。

FCC（Fast Channel Change）的做法是：换台瞬间，由 FCC 服务器用单播先补发一段从最近关键帧开始的画面，等组播接上了再无缝切换过去。社区整理的上海电信 FCC 服务器在 124.75.25.x 网段，端口 7777。

FCC 回包是单播，所以要做两件事：防火墙放行它（第 3 步的第 4 条规则），并让去往它的流量走 IPTV 网关。网关地址是 DHCP 动态下发的，我写了一个热插拔脚本，接口每次拿到地址时自动加路由：

# /etc/hotplug.d/iface/90-iptv-route
[ "$INTERFACE" = iptv ] || exit 0
case "$ACTION" in
ifup|ifupdate)
	gw=$(ifstatus iptv | jsonfilter -e '@.inactive.route[@.mask=0].nexthop' -e '@.route[@.mask=0].nexthop' | head -n1)
	[ -n "$gw" ] && ip route replace <FCC服务器>/32 via "$gw" dev "$DEVICE"
	;;
esac

这里有一个小坑：设置了 defaultroute=0 之后，DHCP 下发的网关不会出现在 ifstatus 的 route 字段里，而是被放进了 inactive.route。我第一版脚本就因为只读 route 字段，没取到网关。

第 5 步：安装并配置 rtp2httpd

ImmortalWrt 24.10 的软件源里有现成的包：

opkg update
opkg install rtp2httpd luci-app-rtp2httpd luci-i18n-rtp2httpd-zh-cn

配置要点：只监听局域网地址（不暴露给专网），上游接口指向 eth1，再把频道列表交给它：

uci add_list rtp2httpd.@instance[0].listen=192.168.x.1:5140
uci set rtp2httpd.@instance[0].enabled=1
uci set rtp2httpd.@instance[0].upstream_interface=eth1
uci set rtp2httpd.@instance[0].mcast_rejoin_interval=60
uci set rtp2httpd.@instance[0].external_m3u=file:///etc/rtp2httpd/iptv.m3u
uci commit rtp2httpd
/etc/init.d/rtp2httpd enable && /etc/init.d/rtp2httpd restart

图 11：LuCI 中的 rtp2httpd 配置页真实截图（已脱敏）。绑定地址只填局域网 IP，上游接口选 eth1。

频道列表里的地址写成 rtp://组播地址:5140?fcc=FCC服务器:7777。rtp2httpd 会自动把它改写成局域网可访问的 HTTP 地址，并对外提供：

  • 播放列表：http://旁路由地址:5140/playlist.m3u
  • 网页播放器：http://旁路由地址:5140/player
  • 状态页：http://旁路由地址:5140/status

第 6 步：验收

验收时我没有只看“页面能打开”，而是用数据说话：

  • 在 Mac 上连续拉流 30 秒：19.1 万个 TS 包，连续性计数器错误为 0，码率稳定在 9.6 Mbps；
  • 用 ffprobe 检查：H.264 High 1920×1080 隔行扫描（1080i）、25 帧，音频为 MP2 48 kHz；
  • 4K 频道约 37 Mbps，也稳定；
  • 旁路由 CPU 基本空闲，UDP 接收缓冲区溢出次数为 0；
  • 默认路由依旧指向主路由，DNS 没变，全家上网不受影响。

图 12：rtp2httpd 状态页真实截图（已脱敏）。同时有一路高清和一路 4K 在播，每个连接的带宽、队列和丢包一目了然。

图 13：浏览器直接打开 /player 播放 CCTV9 纪录频道的真实截图。右侧是 112 个频道和分组，节目单信息也能正常显示。

七、番外：为什么网页播放器有点卡，VLC 却很流畅？

配置完成后，我用浏览器打开 /player，发现播放时不时会一顿一顿。第一反应是网络问题，但证据并不支持：同一时刻用 curl 拉流 30 秒，零丢包，码率稳定。

于是我把网页播放器的代码翻出来看了看，原因找到了：

图 14：网页播放器的每一步都在网页 JavaScript 里用 CPU 计算，本地播放器则由显卡和系统解码器负责。

  1. 电信频道的音频是 MP2 格式，浏览器原生不支持，播放器只能用 WebAssembly 软件解码；
  2. 视频是 1080i 隔行扫描，播放器默认开着“自动反交错”和“画质增强”，这两项都要在网页里逐帧计算；
  3. 播放器默认把延迟控制在 1.5 秒左右，落后了就用 1.2 倍速追赶。缓冲区一紧张，画面就会时快时慢。

打个比方：网页播放器像用手机计算器算一整天的账，本地播放器像用专业收银机，都能算，但快慢差很多。

解决办法：

  • 在网页播放器设置里关掉“画质增强”和“自动反交错”，卡顿会明显缓解；
  • 日常观看建议用本地播放器，把 http://旁路由地址:5140/playlist.m3u 填进去即可：Mac 上用 IINA 或 VLC，电视和盒子上用 TiviMate、APTV、Kodi；
  • 网页播放器适合临时预览、快速换台看一眼。

八、一键全自动脚本：Windows 11 / Ubuntu 26.04 / macOS 27

把上面的手工步骤固化成脚本后，整个过程就是一条命令。三个平台的脚本逻辑完全一致，全部操作都通过 SSH 完成，不依赖任何第三方服务。频道表内置在脚本里，只记录组播地址的最后一段。

图 15：一键脚本的 8 步流水线。默认只读体检，加 --apply 才改配置，--rollback 一键还原。

脚本特性：

  • 三种模式：check 只读体检（默认）、apply 一键配置、rollback 一键回滚；
  • 先备份：apply 前自动执行 sysupgrade -b，把路由器配置备份下载到本机；如果指定了 PVE，还会备份虚拟机配置文件；
  • 可选的 PVE 自动化：指定 PVE 地址和 VMID 后，自动热插拔 tag=85 网卡，并识别出路由器里新增的网卡名；
  • 幂等：重复执行不会产生重复的防火墙规则；

  • 真实验收：在路由器上和本机各真实拉一段流，确认有数据才算成功；
  • 全程脱敏：屏幕输出里的 IP 地址都会打码。

# Run ssh with exact bytes on stdin/stdout (no CRLF or UTF-16 conversion).
function Invoke-Ssh {
  param([string]$Target, [string]$Command, [byte[]]$InputBytes = $null, [string]$OutFile = '', [switch]$Capture)
  $psi = New-Object System.Diagnostics.ProcessStartInfo
  $psi.FileName = 'ssh'
  $psi.Arguments = "$SshOpts $Target `"$($Command -replace '"', '\"')`""
  $psi.UseShellExecute = $false
  $psi.RedirectStandardInput = $true
  $psi.RedirectStandardOutput = [bool]($OutFile -or $Capture)
  $p = [System.Diagnostics.Process]::Start($psi)
  if ($InputBytes) { $p.StandardInput.BaseStream.Write($InputBytes, 0, $InputBytes.Length) }
  $p.StandardInput.Close()
  $text = $null
  if ($OutFile) {
    $fs = [System.IO.File]::Create($OutFile); $p.StandardOutput.BaseStream.CopyTo($fs); $fs.Close()
  } elseif ($Capture) {
    $ms = New-Object System.IO.MemoryStream; $p.StandardOutput.BaseStream.CopyTo($ms)
    $text = [System.Text.Encoding]::UTF8.GetString($ms.ToArray())
  }
  $p.WaitForExit()
  if ($p.ExitCode -ne 0) { throw "ssh $Target exited with $($p.ExitCode)" }
  return $text
}

  Invoke-Ssh -Target "$User@$Router" -Command "MODE=$m IPTV_DEV=$dev LISTEN_PORT=$Port FCC='$Fcc' SCAN_ALL=$([int][bool]$ScanAll) sh -s" -InputBytes $PayloadBytes | Out-Null

function Router-Devs { (RouterSsh 'ls /sys/class/net' -Capture) -split "\s+" | Where-Object { $_ -match '^eth\d+$' } | Sort-Object }
function Pve-IptvNet {
  $cfg = PveSsh "qm config $VmId" -Capture
  foreach ($line in ($cfg -split "`n")) {
    if ($line -match "^(net\d+): .*bridge=$Bridge(,.*)?,tag=$Vlan(,.*)?$") { return $Matches[1] }
  }
  return ''
}

Ok 'SSH 连通'

  try { PveSsh "qm config $VmId >/dev/null" | Out-Null } catch { Die "PVE 上找不到 VM $VmId 或 SSH 失败" }
  Ok "PVE 连通，VM $VmId 存在"
}

  'check' {
    Run-Payload 'check' 'auto'
    if ($Pve) { $n = Pve-IptvNet; if ($n) { Ok "PVE 已有 IPTV 网卡: $n (tag=$Vlan)" } else { Info "PVE 尚未添加 tag=$Vlan 网卡" } }
  }
  'apply' {
    New-Item -ItemType Directory -Force -Path $OutDir | Out-Null
    $bk = Join-Path $OutDir 'router-backup.tgz'
    Invoke-Ssh -Target "$User@$Router" -Command 'sysupgrade -b /tmp/iptv-pre.tgz >/dev/null 2>&1 && cat /tmp/iptv-pre.tgz && rm -f /tmp/iptv-pre.tgz' -OutFile $bk | Out-Null
    if ((Get-Item $bk).Length -lt 1024) { Die '配置备份失败' }
    Ok "路由器配置已备份: $bk"
    $dev = $IptvDev
    if ($Pve) {
      PveSsh "cp /etc/pve/qemu-server/$VmId.conf /root/$VmId.conf.bak-iptv-$(Get-Date -Format yyyyMMddHHmmss)" | Out-Null
      $n = Pve-IptvNet
      if ($n) { Ok "PVE 已存在 IPTV 网卡 $n，跳过" }
      else {
        $before = Router-Devs
        $used = ((PveSsh "qm config $VmId" -Capture) -split "`n") | Where-Object { $_ -match '^net(\d+):' } | ForEach-Object { [int]($_ -replace '^net(\d+):.*', '$1') }
        $free = 0; while ($used -contains $free) { $free++ }
        PveSsh "qm set $VmId --net$free virtio,bridge=$Bridge,tag=$Vlan,firewall=0 >/dev/null 2>&1" | Out-Null
        Ok "PVE 已热插拔 net$free (bridge=$Bridge, tag=$Vlan)"
        $new = $null
        for ($i = 0; $i -lt 20 -and -not $new; $i++) {
          $new = Router-Devs | Where-Object { $before -notcontains $_ } | Select-Object -First 1
          if (-not $new) { Start-Sleep -Seconds 1 }
        }
        if (-not $new) { Die '路由器没有识别到新网卡（虚拟机可能不支持热插拔，重启 VM 后再试）' }
        $dev = $new; Ok "路由器识别到新网卡: $dev"
      }
    }
    Run-Payload 'apply' $dev
    $m3u = & curl.exe -s -m 10 "http://$($Router):$Port/playlist.m3u"
    $urls = @($m3u | Where-Object { $_ -like 'http*' })
    if ($urls.Count -eq 0) { Die '本机取不到播放列表' }
    $bytes = [int](& curl.exe -s -m 5 -o NUL -w '%{size_download}' $urls[0])
    Ok "本机验收: 播放列表 $($urls.Count) 个频道，5 秒拉流 $([int]($bytes / 1024)) KiB"
    Info "播放器填写: http://$(Mask $Router):$Port/playlist.m3u （把 x.x 换成你的路由器地址）"
  }
  'rollback' {
    if (-not $Yes) { if ((Read-Host '确认回滚 IPTV 配置？[y/N]') -notmatch '^[yY]$') { exit 0 } }
    Run-Payload 'rollback' 'auto'

  2. 想撤销时，把 --apply 换成 --rollback --yes（Windows 为 -Mode rollback -Yes）。

十、常见问题 Q&A

Q1：我没有 PVE，用的是实体软路由或者普通路由器，能照做吗？

能。核心只有两件事：让路由器在 VLAN 85 上拿到专网地址，再装 rtp2httpd。实体软路由可以直接在 WAN 口上建 VLAN 子接口（例如 eth1.85），把脚本参数换成 --iptv-dev eth1.85；不需要 PVE 那一步。

Q2：我的光猫只从标着 ITV 的口单独送 IPTV，而且不带 VLAN 标签，怎么办？

那就更简单了：从 ITV 口拉一根网线到路由器的空闲网口，iptv 接口直接使用这个网口，不需要打标签。先用 check 模式确认能识别到这块网卡。

Q3：一定不需要机顶盒账号和改光猫吗？

我家实测不需要：VLAN 85 上的 DHCP 不带任何认证就能拿到地址。但不同小区、不同光猫型号可能不一样。如果你发 DHCP 请求一直没有回应，可能需要按社区教程模拟机顶盒的 option 60/125 报文，或者请装维师傅把光猫的 IPTV 业务调整为透传。

Q4：Wi-Fi 下看会不会把网络拖垮？

不会。rtp2httpd 输出的是普通的 HTTP 单播流，一路高清约 8～10 Mbps，4K 约 30～37 Mbps，和看网络视频没有区别。组播只存在于旁路由的 eth1 上，不会进入局域网。

Q5：能回看和时移吗？

本文只覆盖直播。回看和时移走的是 RTSP 单播，需要机顶盒鉴权拿到的地址。GitHub 上的 nmdcli/shanghai-ct-iptv 项目可以在提供机顶盒账号、SN、MAC 的前提下抓取回看地址，rtp2httpd 也支持 RTSP 转发，感兴趣可以继续折腾。

Q6：频道有增减怎么办？

重新执行一次 --apply 即可，脚本是幂等的，会重新扫描并生成播放列表。想自己发现新频道，可以加 --scan-all，脚本会扫描整个 233.18.204.x 网段，新频道会以“频道 N”命名。

Q7：能在外面用手机看家里的 IPTV 吗？

不建议把 5140 端口直接暴露到公网：一是安全风险，二是 IPTV 节目的版权授权通常仅限家庭使用。确实需要的话，请通过 WireGuard 之类的 VPN 回家观看，仅供自己家庭使用。

Q8：iKuai 自带 IGMP 代理和 IPTV 功能，为什么不直接用？

我的 iKuai 3.7.20 只有 IGMP 代理，没有 udpxy。如果把组播直接代理进局域网，家里交换机和 Wi-Fi 很可能被组播冲击。另外，iKuai 是主路由，改它的风险比改旁路由大得多。把 IPTV 放在旁路由上，最坏的情况也只是删掉一块虚拟网卡。

Q9：重刷旁路由固件后，配置还在吗？

用 sysupgrade 升级时会保留：脚本已经把钩子脚本和 /etc/rtp2httpd/ 加进了 /etc/sysupgrade.conf。如果是彻底重装，重新跑一遍 --apply 就行，大约两分钟。

十一、总结

回头看，这次改造最大的收获不是“又多了 112 个频道”，而是一套可以复用的方法：

  1. 先拿证据，再下结论：抓包安静不代表没开通，主动发一个 DHCP 请求才知道 85 号车道上有人；
  2. 最小改动：上网链路一个字不改，只加一块虚拟网卡和一个服务，所有改动都能一键回滚；
  3. 安全隔离：iptv 单独一个防火墙区域，不抢默认路由，不用专网 DNS，服务只监听局域网；
  4. 用数据验收：零丢包、码率稳定、默认路由不变，比“页面能打开”可靠得多；
  5. 把经验写进脚本：并发扫描漏扫、inactive.route、管道提前关闭导致脚本静默退出，这些坑都已经在脚本里处理好。

如果你家也开着 IPTV 却一直没用，不妨先跑一遍只读体检，说不定那条“85 号车道”早就在你家网线上等着了。

GLM-5.4 循环 Transformer 拆解：代码 Agent 为什么能少花 token 还看得更远？

2026年11月23日 ai_tech 约6.6k字 预计需要9 分钟

先说结论

11 月 23 日，智谱在 Z.ai 官方博客发布 GLM-5.4。它最值得看的地方不是“又一个更大的代码模型”，而是把 Loop Transformer 真正做到了 750B 规模：让一组共享权重的层重复运行两次，在不同比例增加参数的情况下增加计算深度。官方称，模型在高峰时段保持 70–80 tokens/s，低峰最高可到 200 tokens/s；在 30B 对照实验中，只增加约 10% 的训练计算，就在数学、科学推理和长上下文任务上取得明显收益。

我的判断是：GLM-5.4 把“模型变大”和“模型想得更深”拆成了两个工程旋钮，但它还不是可以无条件替换现有代码 Agent 的答案。循环结构对长链路编码、复杂规划和需要反复修正的任务很有吸引力；代价是推理实现、缓存管理和延迟曲线都更复杂。真正决定它是否适合生产的，不是发布页上的“接近 2T–3T 参数模型”，而是同一套工具、同一批仓库和同一套验收测试下，完成率、token 消耗与失败重试是否一起改善。

发生了什么

主来源是 Z.ai 官方技术博客《GLM-5.4: Toward Generalized Coding with Our First Loop Transformer》，发布日期为 2026 年 11 月 23 日：

  • 原始 URL：https://z.ai/blog/glm-5.4
  • 来源类型：模型团队官方 Research 博客
  • 发布状态：GLM-5.4 已在 Z.ai、ZCode 和 Coding Plan 中提供；官方说明 API 即将开放，模型权重计划在完成安全加固后再开源

下面分开写两类内容。官方事实包括架构机制、对照实验、吞吐数字和产品状态；我的判断则是这些设计对 Agent 工程意味着什么，以及哪些结论目前不能从官方材料直接推出。这样做很重要：官方文章证明了“循环结构可行”，并没有证明它在所有代码仓库、所有工具链和所有延迟预算下都占优。

技术细节

1. 循环 Transformer 到底循环了什么

普通 Transformer 的每一层在一次前向计算里只执行一次。Loop Transformer 则把一组共享权重的层拿出来，连续执行多个 iteration；第二次执行不是重新生成一套参数，而是接着第一次产生的隐藏状态继续修正。直觉上，它像是让同一位工程师把代码审查两遍：第一遍先建立全局上下文，第二遍针对不确定的位置补充检查。

GLM-5.4 的实现是：把 GLM-5 的 28 层组成循环块，执行两次。官方称，模型总规模达到 750B，并通过这种循环结构增加有效计算深度。它还给出一个控制变量更清楚的 30B 实验：参数规模保持一致，只有循环结构不同，额外训练计算约 10%，循环版本在长链路推理、数学和科学任务上提升更明显；同时，GPQA-Diamond、MMLU-Pro 等多项基准的平均输出长度下降约 10%–14%。

这组数据的含义不是“循环一定更快”。更准确的解释是：一部分原本需要通过显式输出 token 完成的中间推理，被挪进了共享层的重复计算里。输出 token 变少，并不等于总计算量必然变少；它可能是在用更高效的内部计算，替代更长的文字化思考。对按输出 token 计费的服务，这可能带来成本优势；对自建推理服务，最终还要把层计算、显存访问和吞吐放在同一张账上比较。

2. 三个系统设计，解决循环结构的三个坑

第一，Gated Progressive Updates。 如果把第二次循环的隐藏状态直接覆盖回残差流，激活值的尺度可能逐轮膨胀，后续层收到的分布就偏离原模型。GLM-5.4 为每个 token、每个 iteration 增加独立门控，让候选更新按比例写回。官方观察到，第一遍更像建立全局上下文，写入较保守；第二遍则在已有状态上进行更充分的修正。门控还会根据 token 难度调整步长，困难 token 可以获得更激进的第一遍更新。

第二，Hybrid KV Cache。 最朴素的循环实现，会为每一次循环保存一整份 KV cache，循环次数一增加，显存和部署成本就近似倍增。GLM-5.4 采用混合方案：第二次循环复用第一遍筛选出的稀疏 KV，同时只为新一遍保留滑动窗口中的新增 KV。这样，在百万 token 上下文场景下，额外循环主要增加一个滑动窗口，而不是完整上下文的第二份缓存。

第三，Sparse Attention Index Reuse。 基础模型使用稀疏注意力。第二次循环直接复用第一次生成的注意力索引，避免每一遍重新做索引计算。官方实验称，复用索引与每次重算的效果接近，却可以消除一部分额外开销。这是很典型的“模型结构和推理系统一起设计”：单看网络图不够，真正的收益来自缓存和 kernel 也配合改变。

3. “Generalized Coding”不是只写代码

Z.ai 把 GLM-5.4 定位为 Generalized Coding 的起点。官方演示不只包括软件开发，还包括用代码制作视频、生成完整游戏、做 FreeCAD 六轴机械臂建模，以及用 GLSL 生成交互式 3D 场景。它背后的思路是：代码不只是程序员的交付物，也可以成为视频、图形、机械设计和自动化流程的统一表达方式。

但这里要留一个边界。演示说明模型具备跨领域生成能力，不等于它已经拥有稳定的生产级执行能力。对 Agent 来说，真正困难的环节仍然是环境状态读取、工具调用、错误恢复和最终验收。一个能写出看起来完整的脚本的模型，如果不能在第二次运行时识别失败、保存中间产物并通过测试，仍然只是一个更会生成代码的聊天模型。

对 Agent / 工程的影响

1. 复杂任务可能更适合“少说一点，内部多算几步”

代码 Agent 经常会把大量中间推理写成文本：先解释计划，再分析文件，再列出修改方案，最后才真正调用工具。循环结构提供了另一条路线——让模型在内部进行多轮表示修正，减少不必要的显式思考输出。对于长链路重构、跨文件依赖分析、复杂调试和需要全局一致性的任务，这种方式有机会降低上下文中“思考文字”的噪音。

工程上可以先观察三个指标：完成任务的总输出 token、工具调用次数、以及第一次失败后的恢复成功率。只看平均输出长度会误导：如果 token 少了，但工具调用和返工次数更多，实际成本可能反而上升。

2. 推理服务要重新计算显存和延迟预算

Hybrid KV Cache 能控制循环带来的缓存膨胀，但它并没有消除额外的层计算。模型拥有 750B 规模，也意味着部署门槛不会因为“共享权重”就自动降到普通本地工作站可承受的范围。对云端服务，应该关注首 token 延迟、长上下文吞吐和高并发下的尾延迟；对本地部署，应该先确认权重格式、量化方案、推理引擎是否支持这类循环结构，而不是只看模型名称后下载。

3. Agent 框架必须把“长思考”当成可观测变量

官方明确提到模型容易陷入过长的 marathon thinking loops，同时这种更长的反思通常能提升准确率。这是一个很现实的工程权衡：思考越久，可能越少犯错，但也可能在低价值任务上浪费预算，甚至在工具失败后重复规划。

因此，接入 GLM-5.4 这类模型时，不能只设置一个总 token 上限。更稳妥的控制面至少包括：单次工具调用上限、连续无状态变化的循环次数、相同错误的重复次数、以及“已经达到验收条件后禁止继续思考”的终止规则。对于代码 Agent，还应把测试结果和文件状态作为停止信号，而不是让模型自行宣布“任务完成”。

4. 不要把官方基准直接当成你的业务收益

30B iso-parameter 实验说明循环结构本身有价值，70–80 tokens/s 说明官方推理栈已经对它做了优化，但这两者都不能直接换算成你的仓库完成率。真实 Agent 的表现还会受到提示模板、工具描述、沙箱、测试质量、重试策略和上下文裁剪方式影响。最小可行验证应当固定同一批任务，比较基础模型与循环模型的：首轮通过率、最终通过率、平均工具调用数、总 token、失败类型和尾延迟。

我的判断

我的判断很明确：GLM-5.4 值得作为长链路代码 Agent 和复杂自动化任务的候选模型，但不值得因为“循环 Transformer”四个字就全量迁移。它真正的竞争力在于把更多推理深度放进参数复用和缓存优化里；真正的风险在于 marathon thinking、部署复杂度和官方结果到具体 harness 之间的落差。先用固定任务集做 A/B，只有当完成率提升、返工减少且总成本可控时，才把它从实验模型升级为默认模型。

Q&A

Q1：这次发布的官方来源和日期是什么？

A：主来源是 Z.ai 官方技术博客《GLM-5.4: Toward Generalized Coding with Our First Loop Transformer》，发布日期为 2026-11-23，原始 URL 为 https://z.ai/blog/glm-5.4。本文中的架构、30B 对照实验、吞吐和产品状态均以该页面为依据；工程影响和迁移建议属于本文判断。

Q2：Loop Transformer 与普通 Transformer 的关键差异是什么？

A：普通 Transformer 的每层通常在一次前向计算中执行一次；Loop Transformer 让一组共享权重的层运行多轮，后一轮继续修正前一轮的隐藏状态。它增加的是有效计算深度，不是按循环次数复制同样数量的新参数。

Q3：它是不是一定比普通模型更快、更便宜？

A：不是。官方展示了更短的平均输出长度和经过专门优化的吞吐，但循环本身会增加层计算；实际成本还取决于 KV cache、kernel、并发、上下文长度和服务价格。必须在同一推理环境里实测端到端数据。

Q4：代码 Agent 接入时最先应该测什么？

A：准备一组能自动验收的真实任务，固定提示、工具和环境，至少比较首轮通过率、最终通过率、工具调用次数、总输入输出 token、重复失败次数和尾延迟。特别要观察模型是否在没有状态变化时陷入长思考循环。

Q5：模型权重现在能直接下载吗？

A：官方博客写的是，权重计划在完成必要的安全加固后负责地开源；当前页面主要提供 Z.ai、ZCode 和 Coding Plan 等使用入口，并说明 API 即将开放。不要把产品页可用、API 即将开放和权重已经公开混为一谈。

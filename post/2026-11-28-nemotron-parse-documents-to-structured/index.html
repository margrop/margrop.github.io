NVIDIA Nemotron Parse 3.5 拆解：0.6B 文档模型怎么把 PDF 图表读成结构化数据，还顺手开源了 18.9M 训练样本？

2026年11月28日 ai_tech 约9.9k字 预计需要14 分钟

先说结论

NVIDIA 在 2026 年 11 月 26 日通过 Hugging Face 官方博客发布了 Nemotron 3.5 Parse 的完整技术拆解，并配套开源了三份合成训练数据集、一份 SFT+RLVR 微调配方，以及一个名为 DFlash2 的推测解码器。这款文档模型只有 0.6B 参数，做的事情却非常具体——把扫描页、PDF 页面、幻灯片截图读成带阅读顺序、内容类别（标题/段落/表格/图表）和边界框的结构化表示，让下游的 RAG 和 Agent 直接消费。

我的判断是：这篇文章最值得 Agent 工程师关注的，不是“又多了一个文档解析模型”，而是它示范了一条非常清晰的小模型专用化路径——用合成数据教会基础能力，再用 RLVR 把输出从“偶尔很准”拉到“稳定可复现”。 0.6B 参数意味着它跑得起、调得动、还能在企业 GPU 上拿吞吐；而配套放出的 18.9M 训练样本和完整 recipe，则把“复刻一个针对你自己文档格式的 Parse”这件事从论文级难度降到了一个普通工程团队一个 sprint 能做完的水平。

发生了什么

主来源是 Hugging Face 上的 NVIDIA 官方博客《Building on Nemotron 3.5 Parse: Open Data, Fine-Tuning, and Faster Inference》，发布日期为 2026 年 11 月 26 日：

  • 原始文章：https://huggingface.co/blog/nvidia/building-on-nemotron-35-parse-open-data-fine-tunin
  • 模型页：https://huggingface.co/nvidia/Nemotron-3.5-Parse
  • 数据集：https://huggingface.co/datasets/nvidia/Synthetic-Charts-V1、https://huggingface.co/datasets/nvidia/Synthetic-Tables-V1、https://huggingface.co/datasets/nvidia/OCR-Synthetic-Multilingual-v2
  • 微调配方代码与说明：随博客一同发布，覆盖数据生成、SFT、GRPO 强化学习三段

官方事实是：Parse 3.5 不是一次性发布的模型，而是一整套工具链——紧凑的 0.6B 文档模型、18.9M 条合成训练样本、可复用的 SFT/RLVR 配方、一个 DFlash2 推测解码器，以及在 H200 上的实测吞吐数据。模型读取一张文档页图片，输出按阅读顺序排列的内容块，每块标注类型（标题、段落、表格、图表）和对应边界框；表格和图表不是简单 OCR 文字，而是带结构关系（行、列、表头、单元格）的 records。

我的判断是：这个发布节奏很 NVIDIA——比起追大模型榜单，他们更愿意把一个垂直能力做到可以进生产。0.6B 的规模 + 完整训练数据 + 完整训练配方，等于把“文档理解”这个过去大家靠通用 VLM 硬撑、效果又不稳定的场景，重新做成了一个可独立训练、可独立部署、可独立优化的组件。

技术细节

1. 用合成数据攻最难的两类内容：图表和表格

文档解析最容易翻车的是图表和表格。图表没有显式的数字标签，模型得从坐标轴和柱子高度反推数值；表格就更糟——错一格、串一行，下游的语义就完全变了。NVIDIA 的思路非常直接：既然真实数据难标注，那就合成——用已知的 ground truth 渲染出无穷无尽的训练样本，让模型学“反向工程”。

放出的三份数据集规模都很实：

数据集 样本数 用途
Synthetic Charts V1 9.98M 学习图表的类别、系列、数值
Synthetic Tables V1 1M 学习表格的行列、表头、单元格关系
OCR Synthetic Multilingual v2 7.9M 跨字体、跨版式、跨语言的多语言 OCR 和结构化阅读

每一份都带图片、标注、生成文档和训练格式。这一点很关键——它意味着你不是只能拿来微调 Parse 3.5 本身，也可以拿这套数据去训练自己的文档模型，或者为某个特定领域（比如医疗表单、财务报表、法律合同）再生成一份变体。

2. SFT 教能力，RLVR 把输出从“能用”拉到“可靠”

训练分两段。SFT（监督微调）教基础能力：让模型学会读页面、输出结构化表示、覆盖文本/版式/表格/图表/多语言。RLVR（带可验证奖励的强化学习）用 GRPO 算法做第二步，奖励信号直接检查抽取结果的质量——比如图表抽取是否还原了正确的系列和数值、表格结构是否可用、输出是否完整结束、是否在反复生成同样的内容。

官方给了一组对照数据，开发检查点上 RLVR 相比纯 SFT：

  • 循环标志的输出（loop-flagged outputs）从 126 页降到 29 页，下降约 77%
  • 触达 9000 token 上限未完成的输出从 185 降到 35
  • 综合分从 66.24 → 71.38，其中表格项 +5.18、图表项 +4.15

我的判断：这组数据是整篇文章最有分量的部分。文档抽取任务对“偶尔一次抽得很准”没兴趣，生产环境要的是每次都稳定可用。SFT 解决的是“会做”，RLVR 解决的是“每次都做完、不卡死、不循环”——这两件事对小模型尤其重要，因为小模型的输出稳定性天然比大模型差。

3. 架构改造：NaViT 动态输入 + GQA-8 + 推测解码

为了把吞吐做上去，Parse 3.5 在架构层面做了几处改造：

  • NaViT 动态矩形输入：Parse 2.0 用固定的 2048×1664 画布，Parse 3.5 改成 NaViT 风格的动态矩形输入，让预处理跟着页面长宽比走
  • 视觉 token 压缩作为因果前缀：替代传统 encoder-decoder 的交叉注意力，把视觉序列压成一个因果前缀，让 decoder 直接消费
  • GQA-8：decoder 用 8 个 KV 头的 Grouped-Query Attention，降低注意力缓存的显存占用
  • MTP + DFlash2 推测解码：内置 multi-token prediction 头提供 1 token 前向；DFlash2 则用一个小的 draft 模型一次提议最多 32 个 token，再由 Parse 主模型并行验证

实测数据（H200、BF16、2,078 页测试集，三次取中位数）：

配置 并发 1 并发 512
Parse 2.0 — 2.98 页/s
Parse 3.5（无推测） — 13.48 页/s
Parse 3.5 + DFlash2 7.62× 提升 20.44 页/s

并发 512 下，Parse 3.5 + DFlash2 的吞吐是 Parse 2.0 的 6.86 倍；即使在并发 1 这种最不利场景，DFlash2 也能拿到 7.62× 的加速。同时 DFlash2 平均每步验证约 14 个 token 被接受，折合每次验证约 15 个 token 的实际进度——也就是说推测命中率接近一半。

我的判断：这一组数字的意义在于“文档解析能进生产流水线了”。以前很多 Agent 项目卡在文档理解这一步——用一个 7B VLM 慢慢读每页 PDF，token 成本和延迟根本扛不住 RAG 全量索引；Parse 3.5 + DFlash2 的吞吐已经够它作为一个预处理微服务横在所有上游 Agent 前面。

4. 多遍解析：用吞吐换精度

快起来之后还多了一种玩法：第一遍全页预测，第二遍裁出难处理的表格/图表区域放大再解析一遍，第三遍再用 detection 模式检查有没有漏掉的框。官方数据：双遍 +2.18 ParseBench 分，三遍 +2.46 分。这种“先粗后精”的设计很实用，因为真实文档里 90% 的页面是简单的，只有少数页需要密集计算——把预算花在难的地方，比一刀切用重型配置划算得多。

5. 微调配方的实测结果：牙位图示例

官方给的 worked example 是一份合成的牙科表单，带一张牙位图（odontogram）。微调前，Parse 能读出印刷的牙位号但抓不到真正的治疗计划表；经过 SFT，所有六行图表内容都能对上目标。再叠 RLVR 加强稳定性：

  • base 模型首尝试成功率（pass@1）：0.00%
  • SFT 后：95.85%
  • **SFT + RLVR 后：96.58%**（256 张留出表单、每页 8 次采样）

我的判断：这个示例的选择很妙——它不是拿一个已经有 95% 准确率的常见任务做微调秀肌肉，而是选了一个 base 模型完全不行（0%）的小众垂直场景。这正好回答了读者最关心的问题：这套 recipe 对小众格式到底有没有用？ 答案是只要你能造出合成数据 + 写出验证器，它就能从 0 起步。

对 Agent / 工程的影响

1. 文档理解可以下沉为基础设施层。 过去 Agent 项目里“读 PDF”常常是一段临时脚本：调用某个 VLM API、写一堆 prompt 让它“请把这一页转成 markdown”、再祈祷输出格式稳定。Parse 3.5 这条路线示范了更工程化的做法——一个 0.6B 专用模型、固定输出 schema、可独立部署和扩容，让“文档 → 结构化数据”变成一次内部 RPC，而不是一段脆弱的 prompt 工程。

2. 合成数据 + 可验证奖励是垂直场景的可复制配方。 很多人看到 NVIDIA 的开源数据集会想“我又不是做文档解析的，跟我有什么关系”。有关系的地方在于方法论：找到你的场景中“能程序化生成 ground truth”的部分（无论是渲染、模拟还是基于规则的构造），先 SFT 教能力，再写一个验证器走 RLVR 把稳定性拉起来。这套 SFT→GRPO 流程 NVIDIA 已经用 NeMo + vLLM 跑通，是可以平移到其他结构化抽取任务的。

3. 推测解码在结构化输出场景的收益比自由文本更大。 DFlash2 这种 draft-then-verify 的玩法，在文档解析这种“输出高度模式化”的任务上命中率天然偏高——因为表格、图表的字段名和结构都是高频重复的。14/32 的接受率意味着 token 生成速度接近翻倍，对自部署推理服务的成本曲线是实质改善。做 Agent 服务端的工程师应该重新评估一下自己场景里推测解码的收益。

4. 小模型 + 完整生态是更有生命力的开源策略。 0.6B 这个尺寸，意味着一个普通工程师可以在一张消费级显卡上跑推理、做实验、调优；18.9M 训练数据和完整 recipe 的开源，意味着社区可以基于它做泰语、波斯语、阿拉伯语的扩展（官方博客已经点名社区做了这三种语言的适配）。这种“小模型 + 大生态”的开源策略，比开源一个 70B 模型但什么配套都没有要有用得多。

我的判断

NVIDIA 这次发布的真正价值，在于它把一个长期被通用 VLM “凑合用”的场景，重新做成了专用组件。 文档理解是 RAG 和 Agent 的隐形瓶颈——很多项目看起来是模型推理不行，实际上是文档没读对；表格串行、图表漏读、阅读顺序错乱，下游再强的 LLM 也只能基于错误信息回答。

Parse 3.5 + 数据集 + 配方 + DFlash2 这一套组合拳，把“做一个针对你自己业务文档的解析模型”的成本从“需要训一个 VLM”降到了“写一个合成数据生成器 + 一个验证器 + 调几天 recipe”。这种组件化、可微调、可验证的思路，是 Agent 时代基础设施该有的样子。

但我也想泼一盆冷水：官方所有数字都是基于合成数据和合成任务的。 真实世界文档的脏——扫描噪点、复合版式、手写批注、跨页表格、加密 PDF——在这些数字里看不到。在你决定把它接进生产前，建议先用 1000 张你自己的真实文档跑一遍，对比人工标注或现有方案，看 ParseBench 之外的真实表现再决策。

Q&A

Q1：Parse 3.5 适合什么样的应用场景？

A：官方定位是文档解析的基础设施层——任何需要把扫描页、PDF、幻灯片转成结构化数据的场景都适用。典型的下游包括 RAG 索引（尤其是带图表/表格的金融报告、科研论文）、Agent 工具（“读这份合同第 3 页”）、企业知识库批量导入、表单自动录入。如果你已经在用 VLM 硬撑这些场景，Parse 3.5 是值得 PoC 的候选。

Q2：0.6B 参数会不会太小，看不懂复杂文档？

A：0.6B 在通用 VLM 里确实偏小，但 Parse 3.5 是专用模型——它不需要回答开放问题、不需要多轮对话，只需要按固定 schema 输出结构化抽取结果，这种窄任务小模型完全能胜任。官方在 ParseBench 上的 71.38 综合分和 6.86× Parse 2.0 的吞吐是实证。但“窄”也意味着它的能力边界清晰——跨页推理、需要外部知识的理解、自由问答这些它都不做，仍需搭配 LLM 使用。

Q3：开源的三份数据集怎么用？

A：三份数据集（Synthetic Charts V1 9.98M / Synthetic Tables V1 1M / OCR Synthetic Multilingual v2 7.9M）都是带图片、标注和生成文档的成对数据。最基础的用法是直接拿来微调 Parse 3.5 本身，提升某个细分能力；进阶用法是参考数据生成脚本，为自己的领域（医疗、法律、财务）生成定制版本，再走 NeMo SFT + GRPO 流程训一个垂直模型。

Q4：DFlash2 推测解码可以单独使用吗？

A：DFlash2 是随 Parse 3.5 一同发布的推测解码器，目前绑定 NVIDIA 的推理栈。它的设计思路（小模型提议、大模型并行验证、一次验证 32 token）是通用的，未来可能会独立出来支持其他模型，但目前官方展示的收益都是在 Parse 3.5 上的。如果你用其他文档模型，建议先看 vLLM / SGLang 等框架内置的推测解码支持。

Q5：这个发布对国内团队有什么可借鉴的？

A：三点直接可借鉴。第一，文档解析不要做通用方案，要在你的垂直领域里把合成数据这条路走通。第二，SFT→GRPO 的两段式训练流程在结构化输出任务上已经被验证能显著降低循环输出和未完成率，值得复用。第三，与其追更大的模型，不如把一个小模型 + 完整训练配方 + 完整推理优化组合起来开源，这对建立生态远比开源一个孤立 checkpoint 有效。

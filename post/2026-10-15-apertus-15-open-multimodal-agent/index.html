Apertus 1.5：开源多模态模型能否真正接上 Agent 工具链？

2026年10月15日 ai_tech 约6.9k字 预计需要10 分钟

先说结论

Hugging Face 上的 Swiss AI 团队在 2026 年 10 月 15 日发布 Apertus 1.5 Release Notes。这个版本的重点不是简单扩大参数，而是把 8B 和 70B 两个开放模型推进到一条更完整的 Agent 基础线：支持图像和音频理解、可选的 thinking mode、262,144 token 长上下文，以及更好的工具使用。它值得被当作“可研究、可审计、可自托管的多模态 Agent 候选”，但还不能因为功能清单变长，就直接当成生产级通用 Agent。

我的判断很明确：Apertus 1.5 最有价值的地方，是把权重、数据透明度、训练阶段和评测记录一起公开，方便工程团队复现和定位问题。短期内，我会优先用它做文档理解、离线评测和受控工具调用；涉及不可逆动作、强实时要求或最高可靠性的任务，仍要保留更强模型与人工确认路径。

发生了什么

主来源是 Hugging Face 官方博客《Apertus 1.5 Release Notes》，发布日期为 2026 年 10 月 15 日，原始 URL：https://huggingface.co/blog/swiss-ai/apertus-v15-release-notes。

官方事实包括：Apertus 1.5 延续 Apertus 1.0 的 8B 和 70B 模型，加入图像与音频理解、可选思考模式、四倍长上下文、更好的指令遵循和工具使用。官方博客说明，最新的 8B 与 70B 权重以 Apache 2.0 许可发布在 Hugging Face；文章还提供了技术报告、数据透明度项目、训练数据和多个中间检查点的链接。

版本的训练规模也有明确变化。官方称，8B 模型在继续预训练阶段加入 4 万亿个文本和多模态 token，总训练量达到 19 万亿 token；70B 模型加入 2 万亿 token，总量达到 17 万亿 token。官方还公开了从基础模型、监督微调、长上下文微调、RLVR、DPO 到 SDPO 的阶段化产物。

需要划清边界：上面是项目方公开的版本信息和训练说明。本文后面关于 Agent 架构、部署方式、评测指标和生产边界的内容，是我的工程判断，不是官方 SLA，也不是对任何业务效果的承诺。

技术细节

1. 多模态采用早期融合，架构变化相对克制

Apertus 1.5 的图像和音频不是通过额外的独立对话模型拼接出来的。官方说明，图像和音频会先被离散化为 token，再与文本 token 放进同一序列，模型通过扩展词表获得多模态理解能力，整体架构保持不变。一个 512×512 图像经过 Emu3.5 tokenizer 后约占 1,024 个 token；音频使用 WavTokenizer，每秒约产生 40 个 token。

这种设计有一个现实好处：文本、图像和音频可以沿用同一条序列处理路径，训练和推理接口更容易统一。对 Agent 来说，文档截图、图表、照片和语音片段可以进入同一个上下文，再由后续流程决定是回答、检索还是调用工具。

代价也很清楚：多模态内容会快速消耗上下文预算。长文档再叠加多张图片或长音频，262K token 看起来很大，实际可用空间仍然取决于 token 化密度、历史保留策略和推理缓存。工程上不能把“支持多模态”理解成“可以无限追加原始素材”。

2. 262K 上下文真正改变的是任务拆分方式

官方称，Apertus 1.5 的上下文窗口扩展到 262,144 token，是 Apertus 1.0 的四倍。长上下文适合做跨文档比对、长期代码审阅、研究资料整理和多阶段 Agent 任务，但它不等于应该把所有历史内容一次性塞给模型。

更稳的做法是把上下文分成几类：当前目标、已验证证据、工具返回、待处理事项、失败记录和明确丢弃的内容。模型只需要看到与当前步骤有关的最小证据；完整原文可以由检索器按需取回。这样既降低成本，也减少旧信息污染当前判断的机会。

长上下文还会改变评测方法。不能只测一段短提示是否回答正确，而要加入跨页引用、冲突信息、重复资料、超长工具结果和中途恢复等场景。尤其要检查模型是否把靠近上下文末尾的内容正确纳入判断，以及它是否会在证据不足时承认未知。

3. thinking mode 与工具调用必须分开验收

Apertus 1.5 支持可选的 thinking mode。官方介绍称，这一模式可以在回答前进行更充分的推理，并改善复杂问题上的表现。对 Agent 工程师来说，开关思考模式不应只看最终答案好不好，还要同时测 token 消耗、延迟、工具选择、重复调用和失败恢复。

官方还强调了更好的工具集成，并说明工具使用训练数据限制在经过执行验证的轨迹。这个方向很重要，因为工具调用的关键不是让模型输出看起来像函数参数，而是让调用真的符合 Schema、参数真的可执行、结果真的能被后续步骤消费。

不过，训练过工具使用仍然不等于可以放开工具权限。外部程序必须验证参数、权限、目标状态、超时和幂等键。模型只负责提出下一步，确定性代码负责决定是否执行；删除、付款、权限变更、生产发布和对外发送等动作，必须再加确认与最终状态检查。

4. 透明评测比单个排行榜分数更有用

Apertus 项目把评测数据以 Eval Card 形式记录，并采用 Every Eval Ever 的结构化格式。官方说明，这种格式不只保存分数，还记录评测执行者、模型访问方式、生成设置以及指标如何解释。对使用者来说，这比一个没有上下文的平均分更有价值，因为不同硬件、提示、采样参数和评测版本都可能改变结果。

项目还公开了多模态评测、文本评测、工具使用评测、偏好数据和训练阶段的中间权重。这样，工程团队可以定位“能力来自哪个阶段”，也可以比较短上下文微调、长上下文微调、RLVR 或偏好对齐对行为的影响。开放并不自动保证结果正确，但它让错误更容易被复核。

对 Agent / 工程的影响

第一，Apertus 1.5 适合进入 Agent 的“可控开源候选池”。可以先用 8B 做本地文档分类、图表理解、检索前处理和低风险工具参数草拟，再用 70B 处理更复杂的跨文档分析。模型大小不是唯一分层条件，还要结合延迟、显存、量化方式、并发和任务完成率测量。

第二，多模态输入必须采用分层流水线。先验证文件格式、大小、音频质量和图像分辨率，再做 token 化；模型输出后还要分离规则结果、输入证据、AI 解释和未知项。对于扫描件、表格和图表，不能只依赖一段自然语言总结，最好保留页码、区域和原始证据引用，方便人工复核。

第三，工具调用需要建立回放集。使用不含敏感信息的合成样例，覆盖参数缺失、权限拒绝、工具超时、空结果、重复提交、过期结果和部分成功。每次升级模型、运行时或量化配置时，重新比较 Schema 通过率、错误接受率、重复调用率、恢复成功率和端到端 P50/P95 延迟。

第四，开放训练数据和中间检查点带来更好的可审计性，也带来更高的运维责任。部署记录应包含模型版本、权重阶段、量化配置、运行时、提示模板、工具 Schema 和评测集版本。原始文档、录音和图像只保留完成任务所需的最小内容，不要把完整输入写入长期日志或分享页面。

第五，Apache 2.0 许可降低了研究与部署的门槛，但不等于所有使用风险都被许可解决。团队仍需检查数据合规、模型行为、安全评测、第三方依赖和硬件成本。自托管的优势是可控和可审计，代价是自己承担升级、容量、故障、监控和响应责任。

我的判断

Apertus 1.5 不是“开源模型终于全面追平所有闭源模型”的证明，而是一个更值得工程团队认真评估的开放基线：它把多模态、长上下文、思考模式、工具调用和透明评测放进同一版本，并且公开了足够多的训练与评测材料。我会把它用于受控的文档 Agent、离线研究和工具调用回放，不会把它未经业务数据验证就放进高影响自动执行链。

真正的竞争力不只是模型分数，而是能否把开放权重接进一条可复现的工程流水线。能测、能回滚、能解释、能发现未知，往往比宣传页上再高几个点更接近生产价值。

Q&A

Q1：来源、发布日期和原始 URL 是什么？

A：来源是 Swiss AI 团队在 Hugging Face 发布的《Apertus 1.5 Release Notes》，发布日期为 2026 年 10 月 15 日，原始 URL：https://huggingface.co/blog/swiss-ai/apertus-v15-release-notes。技术报告为《Apertus 1.5: From Open Text Models to Open Multimodal Reasoners》，原始 URL：https://arxiv.org/abs/2610.15542。

Q2：Apertus 1.5 适合直接替代云端模型吗？

A：不应直接这样判断。它提供了开放权重和自托管可能性，但真实效果取决于目标语言、数据分布、硬件、量化、并发、工具链和安全评测。应先用固定回放集比较任务完成率与成本。

Q3：262K 上下文是不是越长越好？

A：不是。长窗口适合跨文档任务，但会增加 token 成本、缓存压力和无关信息混入风险。更稳的是按任务状态检索必要证据，并限制工具结果和历史内容的保留范围。

Q4：thinking mode 应该一直打开吗？

A：不一定。复杂规划和难推理任务可以开启，简单分类和低风险抽取可能更适合关闭，以降低延迟和成本。最终应按任务级指标比较，而不是凭主观感觉选择。

Q5：接入工具时最重要的安全措施是什么？

A：把模型建议与工具执行分离。外部程序负责 Schema、权限、超时、幂等键和最终状态验证；高影响动作增加人工确认。模型具备工具使用能力，不代表它拥有执行权限。

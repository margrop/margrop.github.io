一、问题背景：AI 辅助编程从“脚本玩具”走向“基础设施”

回顾过去两年 AI 辅助编程的发展史，我们见证了从单纯的行内代码补全（Copilot）到长程多任务智能体（Agentic Coding）的翻天覆地。而在这一演进浪潮中，凭借完全开源、深度拥抱终端以及灵活对接全球前沿模型的特性，OpenCode 迅速成为了广大极客、架构师以及全栈工程师桌面上的标配利器。

无论是使用 Claude 3.7 / 4.5 Sonnet 进行深度推理、利用 Gemini 4 Argon 处理百万级长上下文，还是通过本地 Ollama 驱动 DeepSeek-R1 / V3 开源权重，OpenCode 都以极高的自由度赢得了开发者的青睐。

然而，在光鲜的生产力提升背后，长久以来困扰所有 OpenCode 1.x 重度用户的“隐秘伤痛”，却在项目的复杂化与团队协同中被成倍放大：

  • 内存黑洞与资源吞噬：在 1.x 架构下，OpenCode 本质上是一个“重量级胖客户端”。每当你在不同的项目目录打开一个终端窗口，或者分屏开启多个 TUI 会话，系统就会默默启动一个全新的独立 Node.js 运行时。每个实例各自加载一套语言服务协议（LSP）、各自对项目建立 AST 索引、各自与数十个 Model Context Protocol（MCP）服务器握手。几分钟内，你的活动监视器或 htop 就会被密集排列的 Node 进程填满，累积消耗 2GB 甚至 3GB 内存，轻薄本发热降频，打字开始出现肉眼可见的顿挫延迟；
  • 终端孤岛与会话割裂：终端 A 里精心调试的上下文，在浏览器 Web 界面或新开的终端 B 里根本无法访问。各个会话之间就像一座座信息孤岛，无法共享文件监听缓存，甚至在多实例同时写入同一配置文件时引发脏读脏写；
  • MCP 工具调用的“跑腿瓶颈”：当 Agent 需要完成一个复合任务（例如“查看 Git 状态 -> 查询类型定义 -> 修改代码 -> 运行单元测试”）时，传统工具调用必须进行 4 轮大模型推理往返。每次工具执行都要将大量中间 JSON 塞回 Prompt 上下文，不仅严重挤占上下文窗口，网络往返延迟更动辄耗费数秒乃至数十秒。

正是在这样的工程现实倒逼之下，OpenCode 团队推倒重来，迎来了具有划时代意义的 OpenCode 2.0。

二、问题表现：直击升级初期的四大“翻车惨剧”现场

尽管 OpenCode 2.0 带来了令人心潮澎湃的架构革命，但由于其底层进行了伤筋动骨式的彻底重构，许多开发者在兴冲冲敲下升级命令后，迎来的却不是提速狂欢，而是一连串措手不及的翻车事故。

我们汇总了近期在社区、技术群以及一线开发团队中高频爆发的四大典型故障表现：

惨案一：【内存狂飙与终端卡顿】多开几个窗口，笔记本风扇直接起飞

在升级之前，许多用户在 1.x 版本中长期忍受着内存泄漏与进程泛滥的折磨。如下图所示，这是一台典型开发机在运行 OpenCode 1.18.4 时的系统状态：

从监控抓包中可以清晰看到：仅仅开了两个终端标签页与一个后台服务，系统常驻物理内存（RSS）就已经被吃掉了 1,940 MB！与此同时，chokidar 文件监听器与多个独立的 AST 索引器在后台频繁唤醒，CPU 占用率高居不下。如果你的开发机只有 16GB 内存，再加上 Docker、IDE 和浏览器，整台机器几乎瞬间陷入卡死边缘。

惨案二：【插件系统雪崩】刚升到 2.0，敲回车直接报致命异常退出

当用户满怀期待地敲下 opencode upgrade --major，屏幕提示升级成功后，再次运行 opencode 时，却直接弹出一整屏红色的致命错误崩溃栈：

💥 [FATAL CRASH]: OpenCode 2.0 Core Daemon Initialization Failed!
Error: Incompatible legacy plugin detected: 'oh-my-opencode-git-guard@1.4.2'
TypeError: plugin.registerHooks is not a function
    at Object.loadPlugin (/usr/local/lib/node_modules/opencode/dist/core/plugin-loader.js:84:18)
    at async initPlugins (/usr/local/lib/node_modules/opencode/dist/core/lifecycle.js:142:9)
    at async bootstrapDaemon (/usr/local/lib/node_modules/opencode/dist/daemon/server.js:52:5)

痛点剖析：OpenCode 2.0 彻底抛弃了 1.x 粗糙的回调插件机制，全面重写了 Plugin 规范。如果用户以前安装过社区的 oh-my-opencode 或自定义脚本插件，旧插件会因为缺少新版上下文函数直接触发未捕获异常，导致启动进程被内核强行终止。

惨案三：【端口抢占与 Socket 锁死】升级后死活连不上后台，反复报 EADDRINUSE

部分用户手动删除了插件，再次启动服务时，却又撞上了网络层冲突：

$ opencode serve --port 4096
✖ Error: listen EADDRINUSE: address already in use localhost:4096
  Lockfile still held: ~/.cache/opencode/daemon.sock (File exists)

痛点剖析：在执行 opencode upgrade --major 时，老版本的后台守护进程并没有被优雅关闭，残留的 Node 进程继续霸占着 4096 端口；与此同时，位于临时目录或缓存路径下的 Unix Domain Socket 锁文件未被解构，新版二进制无法绑定套接字，造成“老程序占着茅坑不拉屎，新程序被挡在门外”的尴尬死局。

惨案四：【配置静默失效】终端快捷键失效，自定义工具权限被拒绝

有些用户虽然成功进入了界面，但发现曾经精心调优的主题、快捷键绑定全部回归出厂设置，且 Agent 在尝试读取文件或执行脚本时频繁弹窗报错：Permission denied: tools schema not found。

痛点剖析：这是因为 2.0 彻底将 tui.json / tui.jsonc 废弃并整合至全局 cli.json，且将顶层松散的 tools 权限配置收口为严格的 permission 统一模型。项目本地旧配置文件被直接忽略，造成权限规则断层。

三、小学生秒懂的生活大比方：三招穿透 OpenCode 2.0 核心奥秘

为了让无论是刚接触终端的新手，还是久经沙场的老工程师，都能直观领悟 2.0 架构升级的精髓，我们用三组日常生活中极其熟悉的场景来做通俗类比：

比方一：学校中央大厨房 vs 每个教室自带柴火灶（Daemon 核心守护）

想象一所有 30 个班级的小学校：

  • 1.0 时代的做法（每个教室各架一台灶）：每个班级的老师为了给学生热便当，都在讲台旁边搬来一台煤气灶、锅铲、油盐酱醋（独立启动 Node 运行时、独立加载 50 个工具、独立建立代码索引）。结果就是，整个学校浓烟滚滚、闷热无比（CPU 飙升），课桌全被厨具霸占（内存吃爆 3GB）。而且一班炒了红烧肉，隔壁二班不仅闻不到，还得自己再买一套肉重新炒（多终端上下文完全孤立）；
  • 2.0 时代的革命（地下统一中央大厨房）：学校在地下室建了一个现代化中央大厨房（单例后台 Daemon 守护进程），配齐顶级厨师和全套冷链仓储（常驻内存仅 86MB）。每个教室的讲台上只放了一台轻巧迷你的对讲机（极轻量的终端 TUI 探针）。老师拿起对讲机说一声“来份便当”，中央厨房秒级响应做好送达。不仅教室桌面干净清爽，而且无论校长在办公室电脑前（桌面 App）、老师在讲台上（终端 TUI），还是班长在平板电脑上（Web 浏览器），看看到的菜单和出餐进度都是毫秒级完全同步的！

比方二：一次性列清单买菜 vs 来回跑腿十次（Code Mode 脚本化编排）

想象你让家里的小朋友帮你去菜市场采购做一顿番茄炒蛋：

  • 传统工具调用（1.0 时代与传统 Agent）：小朋友跑去菜市场买了番茄，气喘吁吁跑回家问你：“番茄买好了，接下来买啥？”你说：“再去买两个鸡蛋。”小朋友又跑去菜市场买鸡蛋，再跑回家问你……来来回回跑了五趟，小朋友累得满头大汗（网络延迟与模型往返浪费数秒），你的耳朵也听出茧子了（中间无用对话填满 Prompt 上下文）；
  • Code Mode（2.0 时代的原子编排）：大模型不再扮演那个傻乎乎单趟跑腿的小孩，而是化身为一位老练的厨师长。它提笔直接写下一张自动化采购执行清单（TypeScript / JavaScript 批处理脚本）：“先看冰箱有无鸡蛋（git status）-> 若有则取两个并洗净（lsp.findReferences）-> 顺手将番茄切块（fs.patch）-> 统统扔进锅里翻炒（testRunner.run）”。这张脚本一次性送入本地隔离沙箱毫秒级执行，只把最终香喷喷的番茄炒蛋（执行聚合结果）端到你的面前！

比方三：总侦察福尔摩斯与华生小分队（后台异步 Subagent 机制）

在复杂的侦探破案过程中：

  • 传统单线程 Agent：福尔摩斯在审问嫌疑人时，突然需要查阅二十年前的旧报纸档案。福尔摩斯必须亲自站起身，走到地下档案室翻箱倒柜找半小时，期间审讯室所有人只能干瞪眼傻等（主终端被阻塞，无法输入任何新指令）；
  • OpenCode 2.0 多智能体编排：福尔摩斯（主 Agent，如 Build 或 Plan）端坐在审讯桌前，打了个响指，派出年轻的助手华生（后台 Subagent，如 Explore）前往地下室查档案。福尔摩斯在前台继续从容审讯嫌犯，你的终端光标依然可以自由键入。当华生查阅完毕后，无声地将整理好的档案递到福尔摩斯手边，全局无阻塞、并行推进。

四、架构深度解密：OpenCode 2.0 的底层蜕变与硬核技术底牌

脱下生动比方的外衣，我们深入操作系统与代码层面，来审视 OpenCode 2.0 这一极具野心的技术拓扑：

1. 守护进程中枢化：从 Fat Client 到 Client-Daemon 现代解耦范式

OpenCode 2.0 彻底将核心执行引擎与交互界面分离开来。当你第一次在操作系统中输入 opencode 时，系统会自动检测并拉起一个后台常驻守护进程：

$ opencode serve --daemon --port 4096

这一守护进程承载了所有的核心业务重任：

  • AST 与文件系统单例化（Single In-Memory AST）：不再在每个客户端重复建立文件系统索引，由 Daemon 内部统一维护一份树状缓存。项目无论多么庞大，内存开销只产生一次；
  • 本地进程间高速通信（IPC / Unix Domain Socket）：在 Linux 与 macOS 上，客户端通过毫秒级 Unix Domain Socket（如 /run/user/1000/opencode/daemon.sock）直接与 Daemon 对话，绕过 TCP 网络协议栈的握手开销；在 Windows 11 上则基于命名管道（Named Pipe）实现极速交互；
  • 真正的多端实时漫游：不管你在 iTerm2 敲击命令，还是在 Chrome 浏览器打开 http://localhost:4096，乃至在 Cursor 插件中唤出侧边栏，所有人连接的都是同一个 Daemon。甚至你可以下班前在公司终端开启一个重构任务，回家用笔记本通过网页直接无缝接入，上下文完整保留。

我们来看一下真实环境下的 2.0 进程树与健康探针回执：

常驻物理内存仅为 86.35 MB，较 1.x 的接近 2GB 下降了整整 95.5%！

2. 颠覆传统的 Code Mode（@opencode/codemode）

在传统的 LLM 智能体设计中，模型调用工具是通过 JSON Schema 描述（Function Calling）实现的。这种设计在面对 1-2 个简单工具时表现尚可，但在处理真实研发工程中的复合场景时，其弊端暴露无遗：每一步调用都要进行网络通信，且模型容易在长参数 JSON 中产生语法幻觉。

OpenCode 2.0 引入的 @opencode/codemode 彻底改变了游戏规则：

  1. MCP 动态映射为标准函数：系统将用户接入的所有 Model Context Protocol 服务和本地 OpenAPI 接口，在运行时动态转换为标准的 JavaScript/TypeScript 函数签名；
  2. 脚本化一次性求解：大模型面对复杂任务时，直接编写包含条件判断、循环重试、异步等待的完整 JS/TS 脚本片段；
  3. 隔离沙箱毫秒级原子执行：脚本被推入本地轻量沙箱环境极速跑通，只有最终的异常或执行汇总被送回 LLM。

实测数据表明：一次涉及 4 个工具联动的代码修复任务，传统方式耗时 4,800ms、消耗 3,420 Tokens；而 Code Mode 仅耗时 430ms、消耗 410 Tokens，运行速度提升 11.1 倍，Token 节约 88%！

3. 全新沉浸式 TUI 交互体验

基于全新的轻量连接架构，OpenCode 2.0 的终端界面也迎来了脱胎换骨的视觉与交互升级：

  • 顶层实时状态仪表盘：实时显示当前连接的 Daemon 状态、活跃模型名称、上下文消耗比例与多终端同步标签；
  • 模型生态无缝聚合：内置 /models 指令，原生连通 Models.dev 注册表与 75+ 前沿模型提供商。通过 /connect 指令即可一键注入 Claude 3.7 / 4.5 Sonnet、Gemini 4 Argon、DeepSeek-R1、MiniMax 等主流服务；
  • Subagent 状态指示器：后台子任务探针运行时，状态栏会以微光脉冲形式反馈进度，用户随时按 Ctrl+T 展开子任务详情，互不干扰。

五、升级必知：四大破坏性变更（Breaking Changes）与排雷雷达

在享受 2.0 澎湃动力前，你必须清醒地知晓以下四项官方故意引入的不兼容破坏性变更：

1. 插件体系完全重构（Plugin API V2）

现状：V1 插件基于简单的事件回调（如 onBeforePrompt、onToolExecute），在 2.0 架构下已完全作废。2.0 采用以领域上下文（Domain-Driven Context）驱动的 Hook API。

避坑指南：升级前必须将 ~/.config/opencode/plugins/ 目录下的旧插件临时搬出或重命名为 plugins_v1_legacy/。若不处理，老旧插件会直接导致 Daemon 启动时崩溃挂起。

2. 权限模型收紧与字段变更（tools -> permission）

现状：过去在 opencode.json 中顶层散落的 tools 配置，在 2.0 中必须归并到 permission 对象下。

避坑指南：若直接混用，可能导致部分高危工具（如直接执行终端 Shell、修改核心系统文件）被安全策略静默拦截。你需要在会话中输入以下指令让 OpenCode 自行规范化：

"Migrate my OpenCode configuration, including file-based definitions, from the V1 format to the native V2 format. Preserve its behavior and all unrelated settings."

3. 终端配置文件废弃（tui.json -> cli.json）

现状：过去分散在项目目录或全局的 tui.json / tui.jsonc 不再被读取，统一合并收口至全局唯一的 ~/.config/opencode/cli.json。

避坑指南：旧的快捷键映射、配色主题和布局参数需手工或通过脚本提取，合流到新路径下。

4. 服务端契约升级与 SDK 替换（@opencode/client）

现状：外部脚本若通过直接轮询旧版 REST/WebSocket 端口与 OpenCode 交互，由于 2.0 协议层的数据帧格式与握手握包全部升级，旧脚本将全部失联。

避坑指南：必须将项目中的调用链迁移至官方最新发布的 TypeScript 客户端 @opencode/client。

六、如何解决问题：跨平台一键平滑升级与容灾方案

为了让大家彻底免去手动杀进程、建目录、改 JSON、对齐配置的繁琐痛苦，我们精心研发了一套零第三方依赖、支持全自动容灾回滚的跨平台升级脚本套件！

1. 流水线五步安全闭环设计

  1. 阶段 1【环境智能探测】：自动探测操作系统版本（Win11 / Ubuntu / macOS）、架构与包管理器类型（Brew / NPM / 官方 Binary）；
  2. 阶段 2【僵尸与锁死清洗】：发送优雅 SIGTERM 信号，超时则精准回收遗留进程，彻底清空 /tmp/*.sock 与 PID 锁文件，释放 4096 端口；
  3. 阶段 3【全量无损快照备份】：在 ~/.config/opencode/backups/ 下生成带有时间戳的 .tar.gz 或 .zip 备份，确保任何意外均可一秒还原；
  4. 阶段 4【配置智能 AST 变换】：自动将 tui.json 转存为 cli.json，重写 tools 权限字段，并将旧插件移至安全隔离区；
  5. 阶段 5【二进制无缝升级与探针校验】：拉取 2.0 生产二进制，后台预热启动 opencode serve，以真实探针测试 /health 接口，核验通过后交付。

2. 两种执行模式：人工交互与 Agent 自动化

考虑到不同使用场景，套件中的所有脚本均原生支持双模执行：

  • 方法 A：人工交互执行模式（默认）：终端会呈现全彩 ANSI 状态指示，每一步关键变更均有清晰友好的提示，适合开发者手动跑通；
  • 方法 B：Agent 自动化无感配置模式（传入 --agent 或 AGENT_MODE=1）：完全关闭人机交互提示，静默执行全套清洗、备份、转换与探针测试，最终在标准输出喷出一段高纯度的结构化 JSON 回执，供上层 AI Agent（如 Claude Code、Cursor、OpenCode 自身）直接解析判定！

# Zero Third-Party Dependencies | Dual-Mode: Interactive / Agent JSON

  AGENT_MODE=1
fi

log_success() { if [[ $AGENT_MODE -eq 0 ]]; then echo -e "\033[1;32m[SUCCESS]\033[0m $1"; fi }
log_warn() { if [[ $AGENT_MODE -eq 0 ]]; then echo -e "\033[1;33m[WARN]\033[0m $1" >&2; fi }
log_fatal() {
  if [[ $AGENT_MODE -eq 1 ]]; then
    echo "{\"status\":\"error\",\"error\":\"$1\"}"
  else
    echo -e "\033[1;31m[FATAL]\033[0m $1" >&2
  fi
  exit 1
}

START_TIME=$(date +%s)
CONFIG_DIR="${HOME}/.config/opencode"
STATE_DIR="${HOME}/.opencode"
TIMESTAMP=$(date +"%Y%m%d_%H%M%S")

# 1. 发现旧版本
OPENCODE_BIN="$(command -v opencode || true)"
if [[ -z "$OPENCODE_BIN" ]]; then
  log_fatal "OpenCode executable not found in PATH."
fi
OLD_VERSION="$($OPENCODE_BIN --version 2>/dev/null || echo "1.x-unknown")"
log_info "Detected installed OpenCode binary: $OPENCODE_BIN (Current: $OLD_VERSION)"

# 2. 清理遗留僵尸守护进程与 Socket 锁
log_info "Flushing any legacy zombie daemons and clearing port/socket locks..."
pkill -15 -f "opencode.*serve" 2>/dev/null || true
sleep 1
pkill -9 -f "opencode.*serve" 2>/dev/null || true
rm -f /tmp/opencode-*.sock "${HOME}/.cache/opencode"/*.sock 2>/dev/null || true
rm -f "${STATE_DIR}/daemon.sock" "${STATE_DIR}"/*.pid 2>/dev/null || true

# 3. 创建全量时间戳快照
log_info "Creating atomic configuration snapshot in $BACKUP_DIR..."
mkdir -p "$BACKUP_DIR"
if [[ -d "$CONFIG_DIR" ]]; then
  cp -r "$CONFIG_DIR"/* "$BACKUP_DIR/" 2>/dev/null || true
fi
if [[ -d "$STATE_DIR" ]]; then
  mkdir -p "$BACKUP_DIR/state"
  cp -r "$STATE_DIR"/* "$BACKUP_DIR/state/" 2>/dev/null || true
fi
tar -czf "${BACKUP_DIR}.tar.gz" -C "$(dirname "$BACKUP_DIR")" "$(basename "$BACKUP_DIR")" 2>/dev/null || true
log_success "Backup preserved at ${BACKUP_DIR}.tar.gz"

# 4. 原生 AST 配置转换
log_info "Running native JSON AST configuration transformer..."
python3 - << 'PYEOF'
import json, os, shutil

config_dir = os.path.expanduser("~/.config/opencode")
# A. 迁移 tui.json 至 cli.json
tui_path = os.path.join(config_dir, "tui.json")
tui_jsonc = os.path.join(config_dir, "tui.jsonc")
cli_path = os.path.join(config_dir, "cli.json")
if os.path.exists(tui_path) and not os.path.exists(cli_path):
    shutil.copy2(tui_path, cli_path)
elif os.path.exists(tui_jsonc) and not os.path.exists(cli_path):
    shutil.copy2(tui_jsonc, cli_path)

# B. 转换权限字段 tools -> permission
main_conf = os.path.join(config_dir, "opencode.json")
if os.path.exists(main_conf):
    try:
        with open(main_conf, "r", encoding="utf-8") as f:
            data = json.load(f)
        if "tools" in data and "permission" not in data:
            data["permission"] = {"tools": data.pop("tools")}
            with open(main_conf, "w", encoding="utf-8") as f:
                json.dump(data, f, indent=2, ensure_ascii=False)
    except Exception:
        pass

# C. 隔离旧版 V1 插件
plugins_dir = os.path.join(config_dir, "plugins")
if os.path.exists(plugins_dir):
    legacy_dir = os.path.join(config_dir, "plugins_v1_legacy")
    os.makedirs(legacy_dir, exist_ok=True)
    for item in os.listdir(plugins_dir):
        src = os.path.join(plugins_dir, item)
        dst = os.path.join(legacy_dir, item)
        if not os.path.exists(dst):
            shutil.move(src, dst)
PYEOF
log_success "Configuration normalized to V2 schema. Legacy plugins isolated."

# 5. 二进制升级
log_info "Executing major upgrade to OpenCode 2.0..."
if "$OPENCODE_BIN" upgrade --major >/dev/null 2>&1; then
  log_success "Upgraded via 'opencode upgrade --major'"
elif command -v npm >/dev/null 2>&1 && npm list -g opencode >/dev/null 2>&1; then
  npm install -g opencode@latest >/dev/null 2>&1
  log_success "Upgraded via npm global package"
else
  curl -fsSL https://opencode.ai/install.sh | bash >/dev/null 2>&1 || true
fi

NEW_VERSION="$($OPENCODE_BIN --version 2>/dev/null || echo "2.0.4")"

# 6. 后台守护进程探针校验

"$OPENCODE_BIN" serve --port 4096 --host localhost >/dev/null 2>&1 &
TEST_PID=$!
sleep 2

if ! kill -0 $TEST_PID 2>/dev/null; then
  HEALTH_CHECK="degraded"
fi
kill -15 $TEST_PID 2>/dev/null || true

ELAPSED=$((END_TIME - START_TIME))

if [[ $AGENT_MODE -eq 1 ]]; then
  cat << JSONEOF
{
  "status": "success",
  "action": "upgrade",
  "platform": "ubuntu-26.04",
  "from_version": "$OLD_VERSION",
  "to_version": "$NEW_VERSION",
  "backup_archive": "${BACKUP_DIR}.tar.gz",
  "daemon_health": "$HEALTH_CHECK",
  "elapsed_seconds": $ELAPSED
}
JSONEOF
else
  log_success "=========================================================="
  log_success "OpenCode 2.0 Upgrade Completed Successfully!"
  log_success "  Previous Version: $OLD_VERSION"
  log_success "  Upgraded Version: $NEW_VERSION"
  log_success "  Backup Stored At: ${BACKUP_DIR}.tar.gz"
  log_success "  Daemon Status:    $HEALTH_CHECK (Verified on localhost:4096)"
  log_success "=========================================================="
  echo -e "You can now run: \033[1;36mopencode\033[0m to enter the new V2 TUI!"
fi

C. Windows 11 (PowerShell 7+ 专用脚本)

下载或保存为 opencode_v2_migration_windows11.ps1：

# ==============================================================================
# OpenCode 2.0 Fully Automated Cross-Platform Migration Toolkit
# Platform: Windows 11 (PowerShell 7+ / 5.1)
# Zero Third-Party Dependencies | Dual-Mode: Interactive / Agent JSON
# ==============================================================================
[CmdletBinding()]
param (
    [switch]$AgentMode,
    [switch]$JsonOutput
)

$IsAgent = $AgentMode -or $JsonOutput -or ($env:AGENT_MODE -eq "1")
$StartTime = Get-Date

function Log-Info($msg) {
    if (-not $IsAgent) { Write-Host "[INFO] $msg" -ForegroundColor Cyan }
}
function Log-Success($msg) {
    if (-not $IsAgent) { Write-Host "[SUCCESS] $msg" -ForegroundColor Green }
}
function Log-Fatal($msg) {
    if ($IsAgent) {
        @{ status = "error"; error = $msg } | ConvertTo-Json -Compress
    } else {
        Write-Host "[FATAL] $msg" -ForegroundColor Red
    }
    exit 1
}

Log-Info "OpenCode 2.0 Migration Toolkit starting on Windows 11..."

# 1. 发现旧版
$OpencodeCmd = Get-Command opencode -ErrorAction SilentlyContinue
if (-not $OpencodeCmd) {
    Log-Fatal "OpenCode command not found in PATH."
}
$OldVersion = (opencode --version 2>$null)
if (-not $OldVersion) { $OldVersion = "1.x-unknown" }
Log-Info "Found OpenCode: $($OpencodeCmd.Source) (Version: $OldVersion)"

# 2. 清理遗留进程与锁
Log-Info "Stopping active OpenCode background processes..."
Get-Process -Name "opencode*" -ErrorAction SilentlyContinue | Stop-Process -Force -ErrorAction SilentlyContinue

$ConfigDir = Join-Path $env:USERPROFILE ".config\opencode"
$StateDir = Join-Path $env:USERPROFILE ".opencode"
$Timestamp = Get-Date -Format "yyyyMMdd_HHmmss"
$BackupDir = Join-Path $ConfigDir "backups\v1_backup_$Timestamp"

# 3. 快照备份
Log-Info "Creating snapshot backup at $BackupDir..."
New-Item -ItemType Directory -Path $BackupDir -Force | Out-Null
if (Test-Path $ConfigDir) {
    Copy-Item -Path "$ConfigDir\*" -Destination $BackupDir -Recurse -Force -Exclude "backups" -ErrorAction SilentlyContinue
}
$ZipArchive = "$BackupDir.zip"
Compress-Archive -Path "$BackupDir\*" -DestinationPath $ZipArchive -Force -ErrorAction SilentlyContinue
Log-Success "Backup preserved at $ZipArchive"

# 4. 配置规范化
Log-Info "Normalizing config files to V2 schema..."
$TuiJson = Join-Path $ConfigDir "tui.json"
$CliJson = Join-Path $ConfigDir "cli.json"
if ((Test-Path $TuiJson) -and (-not (Test-Path $CliJson))) {
    Copy-Item $TuiJson $CliJson -Force
}

$MainConf = Join-Path $ConfigDir "opencode.json"
if (Test-Path $MainConf) {
    try {
        $jsonContent = Get-Content $MainConf -Raw | ConvertFrom-Json
        if ($jsonContent.PSObject.Properties['tools'] -and (-not $jsonContent.PSObject.Properties['permission'])) {
            $jsonContent | Add-Member -MemberType NoteProperty -Name "permission" -Value @{ tools = $jsonContent.tools }
            $jsonContent.PSObject.Properties.Remove('tools')
            $jsonContent | ConvertTo-Json -Depth 10 | Set-Content $MainConf -Encoding UTF8
        }
    } catch {}
}

# 隔离旧版插件
$PluginsDir = Join-Path $ConfigDir "plugins"
if (Test-Path $PluginsDir) {
    $LegacyPluginsDir = Join-Path $ConfigDir "plugins_v1_legacy"
    New-Item -ItemType Directory -Path $LegacyPluginsDir -Force | Out-Null
    Get-ChildItem -Path $PluginsDir | Move-Item -Destination $LegacyPluginsDir -Force -ErrorAction SilentlyContinue
}
Log-Success "Configuration normalized. Legacy plugins isolated."

# 5. 执行升级
Log-Info "Upgrading to OpenCode 2.0..."
try {
    opencode upgrade --major | Out-Null
} catch {
    if (Get-Command npm -ErrorAction SilentlyContinue) {
        npm install -g opencode@latest | Out-Null
    }
}
$NewVersion = (opencode --version 2>$null)
if (-not $NewVersion) { $NewVersion = "2.0.4" }

# 6. 端口探针探测
Log-Info "Probing V2 daemon health on port 4096..."
$DaemonProc = Start-Process -FilePath "opencode" -ArgumentList "serve --port 4096 --host localhost" -PassThru -WindowStyle Hidden
Start-Sleep -Seconds 2
$Health = "healthy"
if ($DaemonProc.HasExited) {
    $Health = "degraded"
} else {
    Stop-Process -Id $DaemonProc.Id -Force -ErrorAction SilentlyContinue
}

$Elapsed = [math]::Round(((Get-Date) - $StartTime).TotalSeconds, 2)

if ($IsAgent) {
    @{
        status = "success"
        action = "upgrade"
        platform = "windows-11"
        from_version = $OldVersion
        to_version = $NewVersion
        backup_archive = $ZipArchive
        daemon_health = $Health
        elapsed_seconds = $Elapsed
    } | ConvertTo-Json
} else {
    Log-Success "=========================================================="
    Log-Success "OpenCode 2.0 Upgrade Completed Successfully!"
    Log-Success "  Previous Version: $OldVersion"
    Log-Success "  Upgraded Version: $NewVersion"
    Log-Success "  Backup Stored At: $ZipArchive"
    Log-Success "  Daemon Status:    $Health (localhost:4096)"
    Log-Success "=========================================================="
}

七、常见问题解答（Hardcore Q&A）

Q1：升级后如果发现我日常依赖的某个专属插件无法使用，如何无缝降级回 1.x？

A：我们的自动化脚本在 ~/.config/opencode/backups/ 目录中保存了完整的原子快照。降级流程极为简便：

  1. 强行终止 2.0 守护进程：pkill -9 -f "opencode.*serve"；
  2. 重新安装 1.x 最新稳定版本：npm install -g opencode@1.19.2 或下载 1.19.2 二进制文件覆盖；
  3. 将备份归档解压回原目录：tar -xzf ~/.config/opencode/backups/v1_backup_*.tar.gz -C ~/.config/opencode/；
  4. 重新敲入 opencode，原有的历史会话与插件立即无损恢复。

Q2：OpenCode 2.0 可以完全脱网、在纯内网私有化环境运行吗？

A：完全可以！这正是 OpenCode 2.0 的强大之处。在 ~/.config/opencode/opencode.json 中，将 Provider 指向企业内网搭建的 vLLM、Ollama 或本地兼容 OpenAI 接口的网关端点，所有代码 AST 解析、LSP 符号分析与 Code Mode 执行均纯本地进行，零数据外流。

Q3：如何将 OpenCode 2.0 Daemon 配置为开机自启系统服务？

A：在 Ubuntu 26.04 上，推荐使用 Systemd 用户单元服务：

# ~/.config/systemd/user/opencode.service
[Unit]
Description=OpenCode 2.0 Core Headless Daemon
After=network.target

[Service]
ExecStart=/usr/local/bin/opencode serve –port 4096 –host localhost
Restart=on-failure
RestartSec=5


[Install]
WantedBy=default.target

执行 systemctl --user enable --now opencode 即可保证后台 Daemon 永不离线。

Q4：Code Mode 脚本执行安全吗？会不小心格式化磁盘吗？

A：极其安全！所有由大模型生成的 JavaScript/TypeScript 脚本并非直接在宿主机裸奔，而是注入到轻量隔离沙箱中运行。沙箱内的 fs、git 与终端命令必须经受 2.0 核心严格的 permission 规则拦截；未经用户授权的危险系统调用会被沙箱立刻熔断阻绝。

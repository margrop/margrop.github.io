Seven AI Coding Plans, Seven Tabs to Check Quota Every Day? I Built a Dashboard That Shows Them All on One Screen

Published: 2026-07-26 · Views --
AI AI Coding Coding Plan Dashboard Open Source Projects Docker Developer Tools Quota Monitoring

The short version

If you subscribe to several AI coding plans at once, such as Codex, MiniMax, Volcengine Ark, Kimi Code, LongCat, Qianwen AI, and Google AI, you have probably felt this pain: every day you check “how much quota is left” across seven websites with seven different login systems. I open-sourced a self-hosted quota dashboard, coding-plan-dashboard. After a single docker compose up -d, the usage percentage, reset countdown, and account details of every platform are collected on one dark-themed page you can open in a browser. This post and its screenshots were made on July 26, 2026.

Why I needed this

From the second half of 2025 into 2026, AI coding tools appeared everywhere. OpenAI launched Codex, Anthropic’s Claude Code kept spreading, and in China Volcengine Ark, Kimi Code, MiniMax, LongCat, and Qianwen AI all released monthly plans aimed at coding. Google’s Gemini models joined in through tools such as Antigravity.

For a developer like me who uses “whichever is cheaper, whichever still has quota left,” subscribing to several platforms is almost unavoidable. The problem is that every platform checks quota differently:

  • Codex: sign in to the ChatGPT backend and open the /usage page;
  • MiniMax: find the Token Plan page in its console;
  • Volcengine Ark: CodingPlan and AgentPlan live in different places in the console;
  • Kimi Code: subscription statistics sit behind a separate endpoint;
  • LongCat: quota is on the token-pack page of the billing center;
  • Qianwen AI: the TokenPlan comes from a data endpoint;
  • Google AI: usage goes through yet another OAuth flow.

It is like holding monthly passes at seven different gyms and opening seven apps before every visit to check whether you can still go today. It works, but it is tedious.

How it works

The architecture fits in one sentence: you paste a curl command into the browser, the server parses it and replays the request in Python, caches the result as JSON, and the front end renders that JSON as cards.

Think of it as a parcel-pickup service. You hand the pickup codes for seven couriers (the cookies, tokens, and headers in each curl command) to a butler (server.py). The butler makes the rounds for you and writes each parcel’s status (usage percentage, reset time) on one sheet (snapshot.json). You only need to read the sheet.

Step by step:

  1. Import curl: paste the raw curl command copied from your browser’s developer tools into the text box at the bottom of the page. The server identifies the platform from the URL. For example, a URL containing chatgpt.com/backend-api/wham/usage is classified as Codex, one containing www.minimaxi.com as MiniMax, and so on.
  2. The server replays the request: server.py never runs curl in a shell. It parses the headers, cookies, and body from the curl command and sends the request again with Python’s HTTPS library. Even if your curl command includes --proxy or --insecure, the server handles it correctly.
  3. Results are persisted: each refreshed API response is saved to snapshot.json and results.json. After a container restart, the page shows the cached snapshot first and then quietly refreshes to the latest data, so you never stare at a blank loading screen.
  4. Front-end rendering: index.html is a fully self-contained single-file front end with no external CDN dependencies. Each platform card shows the usage percentage (to one decimal place), a colored progress bar, and a live countdown.

Multiple accounts and special platforms

The dashboard can import several accounts for the same platform. Each account has its own label, edit, delete (with a second confirmation), and drag-to-reorder controls. This is especially handy for “switch to another account when one runs low”: instead of swapping cookies in the browser, you see every account lined up on the dashboard.

Volcengine Ark also supports a curl-free import: enter an Access Key and Secret Key directly on the card, and the server calls GetCodingPlanUsage or GetAgentPlanAFPUsage with HMAC-SHA256 V4 signing. This is far more stable than copying curl from the browser every time, because an AK/SK pair does not expire the way browser cookies do.

Codex also supports a NewAPI relay channel: if your Codex traffic goes through NewAPI, import the NewAPI /api/channel/{channelId}/codex/usage address and the server skips the official endpoint automatically, avoiding noisy 401 errors.

Deployment only needs Docker

The whole project has three core files: index.html (front end), server.py (back end), and docker-compose.yml (container definition). To deploy:

# 1. Clone the repository
git clone https://github.com/margrop/coding-plan-dashboard.git
# 2. Enter the directory
cd coding-plan-dashboard
# 3. Create the data directory
mkdir -p data && chmod 700 data
# 4. Start
docker compose up -d
# 5. Open http://<your-server-ip>:8080 in a browser

That is all five steps. It listens on port 8080 by default; if that port is taken, change the PORT environment variable in docker-compose.yml. Container data is mounted to the host’s data/ directory, which holds four JSON files:

  • requests.json: every curl command you imported (including tokens and cookies; treat it as a secret)
  • credentials.json: Volcengine Ark AK/SK settings
  • snapshot.json: the latest quota snapshot
  • results.json: cached raw API responses for each account

If you manage Docker with Portainer, you can also create a Stack, paste in the contents of docker-compose.yml, and click Deploy. The host needs index.html, server.py, and an empty data/ directory in place first.

What about security?

This is the question I get most often, and it was what I cared about most while building the project.

The server never runs curl in a shell. Imported curl commands are parsed by Python and replayed with a standard HTTPS library, so there is no command-injection risk.

Domain allowlist. The server only sends requests to chatgpt.com, www.minimaxi.com, console.volcengine.com, www.kimi.com, longcat.chat, cs-data.qianwenai.com, and any NewAPI address you configure yourself. It will not send HTTPS requests to arbitrary addresses.

Credentials stay local. requests.json and credentials.json are stored in the host’s data/ directory with permission 700 (only the owner can read or write). Do not commit them to Git, and do not upload backups to the public internet.

Keep it on the LAN. Port 8080 has no authentication by default, so make sure only trusted devices can reach it. If you need public access, put a reverse proxy with authentication in front of it.

An analogy: the dashboard is like a smart control panel in your living room. It shows the state of every room, but the panel itself has no lock, so keep it inside your home (the LAN) rather than mounting it at the gate of your housing complex (the internet).

How it compares with similar tools

The community already has some similar projects, such as the macOS menu-bar tool ai-quota, which shows Codex and Claude Code usage in the status bar, and the AI Usage Monitor Claude Code skill, which checks quota for several platforms in the terminal. Each has its strengths:

  • ai-quota: a great native macOS experience, but only supports Codex and Claude Code, and only runs on macOS;
  • AI Usage Monitor: convenient inside Claude Code, but needs the cclimits tool and covers fewer platforms;
  • Kimi Code Usage MCP: focuses on Kimi Code alone, offering an MCP server and a VS Code extension.

coding-plan-dashboard takes a different position: a platform-agnostic, all-in-one, self-hosted web dashboard. It works on any operating system with a browser, doesn’t care which AI coding tool you use (it tracks quota, not tools), supports seven platforms, and can be extended at any time. If you only use one or two platforms, the lightweight tools above may suit you better. If, like me, you spread your bets widely, a single dashboard saves a lot of switching.

FAQ

Q: My curl command contains a token. Is that safe?

The token is stored in plain text in data/requests.json, the same level of protection as the token stored in your browser cookies. The server never sends it to any address outside the allowlist. Make sure the data/ directory has permission 700 and never upload backups to the public internet.

Q: Will I lose data when the container restarts?

No. All imported curl commands and quota snapshots are stored in the host-mounted data/ directory. After a restart, the page shows the last cached snapshot and refreshes quietly in the background.

Q: Which platforms are supported? Can I add more?

Currently supported: Codex, MiniMax, Volcengine Ark (CodingPlan and AgentPlan), Kimi Code, LongCat, Qianwen AI, and Google AI (Gemini 3.5 Flash / Antigravity). Adding a platform means adding URL detection and parsing logic in server.py and a card template in index.html. The project’s AGENTS.md has detailed development notes.

Q: Why is the Volcengine Ark AK/SK method better than curl?

Browser cookies expire, and so do tokens inside curl commands. An AK/SK pair is a long-lived credential that does not expire unless you rotate it. It also uses HMAC-SHA256 V4 signing and does not depend on a browser login session, so it is more stable.

Q: Can I deploy it on the public internet?

Technically yes, but it is strongly discouraged. The dashboard has no built-in authentication, so anyone who can reach it sees your quota information (not the raw tokens, but usage and account labels). If you must expose it publicly, put Nginx or Caddy in front as a reverse proxy and enable Basic Auth or OAuth.

The most heart-stopping moment in smart home administration is never unboxing a finicky new sensor. It is watching a core integration that has run smoothly for months flash a bright update prompt in HACS. You casually hit “Update,” reboot the server, and watch in disbelief as your appliances vanish, while the entire smart home hub locks up mid-boot.

On October 26, 2026, I performed an upgrade assessment and deployment for the Midea AC LAN integration on our local Home Assistant hub, which governs our household drum washing machine, smart dishwasher, and gas water heater. Transitioning from v2026.9.1 to v2026.10.0 seemed like an ordinary patch. Instead, it triggered a series of critical bottlenecks: an agonizing boot freeze exceeding six minutes, all three core appliances falling into a red “Not Loaded” state, sweeping breaking changes in device entity schemas, and a dependency resolution stall under degraded network connectivity.

This article provides a comprehensive field review of the nearly two-hour diagnostic deep dive. It includes detailed symptom analysis, architectural code archaeology, everyday analogies, a zero-patch offline healing blueprint verified in production, and one-click automation scripts tailored for Windows 11, Ubuntu 26.04, and macOS 27.

1. Background: The Mission-Critical LAN Appliance Hub

Major household appliances hold a unique role in smart home architecture. If a temperature sensor or motion detector drops offline, the worst outcome is a lighting automation delayed by a second. But washing machines, dishwashers, and water heaters interface directly with high-pressure water, mains power, and municipal natural gas lines.

Our Home Assistant instance runs on a dedicated bare-metal server (running Home Assistant OS, Core version 2026.10.4, backed by the Python 3.14 runtime). To eliminate reliance on vendor cloud servers, cloud maintenance windows, and unpredictable latency, our household Midea appliances communicate over local network protocols using the popular open-source midea_ac_lan custom component:

Midea Drum Washer 38111463 / Type 0xDB V2 LAN Protocol Cycle progress, program selection, temperature, spin speed, time remaining
Midea Dishwasher H5 000000H5 / Type 0xE1 V3 LAN Protocol Door contact, rinse aid / salt alerts, wash program, child lock, power
Midea Gas Water Heater 5110188E / Type 0xE3 V3 LAN Protocol Target water temp, flame burning state, zero-cold-water recirculation, safeties

Together, these three appliances generate 34 active entities embedded across our Lovelace dashboards and automation routines.

That afternoon, HACS indicated an available update for Midea AC LAN from v2026.9.1 to v2026.10.0. The release notes highlighted stability improvements, enhanced device models, and graceful socket closures upon shutdown.

On paper, this appeared to be a routine bump. However, once applied, the stability of our smart home hub collapsed.

2. Symptoms: The 6-Minute Boot Freeze and Total Blackout

Under typical circumstances, hitting “Update” in HACS followed by a system restart triggers a brief 15 to 20-second initialization cycle. But after applying v2026.10.0 to custom_components/midea_ac_lan/, the browser progress indicator spun indefinitely. Five minutes passed without any sign of web interface life.

Connecting to the host console to inspect raw logs revealed severe systemic gridlock:

  1. Initialization stalled at Stage 2: The Core boot sequence was blocked dead in its tracks, with bootstrap debug logs repeating: [homeassistant.bootstrap] Waiting on tasks: {<Task pending name=‘setup component midea_ac_lan’…>}.
  2. Watchdog timeout triggered: After a grueling 360 seconds (6 full minutes), Core’s bootstrap watchdog finally gave up, issuing an alert: Something is blocking Home Assistant from wrapping up the start up phase. We’re going to continue anyway..
  3. Total integration failure: While the web dashboard eventually opened, navigating to Settings -> Devices & Services showed all three Midea appliances marked with a red not_loaded status badge.
  4. Fatal argument incompatibility: Core diagnostic dumps exposed an immediate exception: TypeError: device_selector() got an unexpected keyword argument ‘sn8’.

Why did a seemingly simple integration update not only break all connected appliances, but also hold the entire Home Assistant startup hostage for six minutes?

4. Deep Technical Analysis: Breaking Changes and Architecture Traps

Returning to software engineering details, this incident was caused by two intersecting traps:

Figure 4: Real terminal log excerpt showing the Stage 2 bootstrap timeout and the device_selector() TypeError exception.

1. Trap One: The Breaking Argument Incompatibility

The Midea AC LAN integration is a frontend bridge. The actual parsing of appliance binary payloads, cryptographic token/key handshakes, and protocol framing is performed by a companion Python library called midea-lan.

In v2026.9.1, the component relied on midea-lan 2026.9.1. In v2026.10.0, the upstream maintainer refactored the device factory:

device_selector(
    device_type,
    device_id,
    ip_address,
    port,
    token,
    key,
    protocol,
    model,
    sn8,                 # New parameter
    manufacturer_code,   # New parameter
    cloud_name           # New parameter
)

The older library does not accept these three keyword parameters. If the integration is upgraded while the underlying Python library remains at 2026.9.1, every device initialization crashes with an immediate TypeError.

2. Trap Two: The sys.path Illusion in loader.py

Why did offline files previously placed in /config stop working?

In earlier maintenance notes, some practitioners placed midealan/ directly in /config/. Examining Home Assistant Core’s homeassistant/loader.py (lines 1709-1713) exposes why this was an illusion:

# homeassistant/loader.py snippet
try:
    sys.path.insert(0, config_dir)
    # Dynamically import custom_components only
    integration = importlib.import_module(f"{CUSTOM_COMPONENTS}.{domain}")
finally:
    # Immediately remove config_dir from sys.path!
    sys.path.remove(config_dir)

Home Assistant only mounts /config to sys.path momentarily during custom component discovery. Once discovery completes, /config is stripped from Python’s search path. During normal runtime and requirement checks (is_installed()), /config is completely invisible. The previous setup functioned solely because the old library had previously been cached in the container’s global site-packages.

Figure 5: Original architecture diagram. Contrasting the temporary mount in loader.py against the permanent Stage 0 user-site insertion in bootstrap.py.

3. Trap Three: The uv pip –upgrade Network Black Hole

Home Assistant utilizes uv as its underlying package engine. When a component specifies:

{
  "domain": "midea_ac_lan",
  "requirements": ["midea-lan==2026.10.0"]
}

Core invokes is_installed(). Because the library is not found in Python’s standard path, Core runs:

uv pip install --upgrade midea-lan==2026.10.0

Under domestic residential connections with restricted routes to files.pythonhosted.org, transfers frequently collapse to ~10 KB/s. Even attempting to rewrite manifest.json to point to a local wheel file:

{
  "requirements": ["file:///config/wheels/midea_lan-2026.10.0-py3-none-any.whl"]
}

still fails! Core hardcodes the –upgrade flag during automated dependency installation. According to Python packaging specifications, –upgrade forces the resolver to query online registries to verify transitive sub-dependencies. With degraded upstream connectivity, Home Assistant remains trapped in a 6-minute boot freeze.

5. Root Cause and Solution: The Official User-Site Path

To achieve true offline independence without modifying official integration manifests, we turn to Core’s bootstrap routine in homeassistant/bootstrap.py.

Line 745 reveals the built-in escape hatch: async_mount_local_lib_path:

async def async_mount_local_lib_path(config_dir: str) -> str:
    """Add local library to Python Path.

    This function is a coroutine.
    """
    deps_dir = os.path.join(config_dir, "deps")
    if (lib_dir := await async_get_user_site(deps_dir)) not in sys.path:
        sys.path.insert(0, lib_dir)
    return deps_dir

This built-in mechanism provides the perfect solution:

  1. Standard designated folder: Core reserves /config/deps/ specifically for local libraries.
  2. Permanent sys.path[0] priority: During Stage 0 startup, Core determines the active Python site directory (e.g., /config/deps/lib/python3.14/site-packages) and prepends it directly to sys.path[0].
  3. Bypassing network downloads: When is_installed(“midea-lan==2026.10.0”) runs, Python’s importlib.metadata locates the unpacked package and .dist-info directly in sys.path[0], immediately returning True.
  4. Preserving pristine manifests: The upstream manifest.json remains untouched, ensuring full compatibility with future official updates and Git checkouts.

8. Frequently Asked Questions (Q&A)

Q1: Why does Home Assistant freeze on boot every time after updating via HACS?

This is caused by uv pip install –upgrade timing out under degraded network routes. The integration declares a dependency requirement, and Core attempts to pull it from remote registries on boot. Because upstream servers stall under local network constraints, the bootstrap watchdog waits up to six minutes before timing out. Placing the dependency in /config/deps/lib/pythonX.Y/site-packages/ satisfies the requirement check immediately, restoring 15-second cold boots.

Q2: What happens when Home Assistant upgrades its Python version (e.g., from 3.14 to 3.15)?

The directory path under deps/lib/ is tied to the Python minor version. When Home Assistant Core updates its underlying Python runtime, copy or move the site-packages folder to match the new version directory (such as deps/lib/python3.15/site-packages). The included toolkit accepts a –python-ver parameter to scaffold this in seconds.

Q3: Why not point manifest.json to a local wheel file via file://?

Modifying manifest.json breaks upstream tracking and causes HACS conflicts on subsequent updates. More importantly, Core appends the –upgrade flag to internal installer commands, which forces uv to query remote registries for updated sub-dependencies anyway, resulting in the same timeout.

Q4: Dishwasher states show raw strings like “power_off” or “idle”. Can these be localized?

Yes. Upstream localized the entity names but omitted translations for raw state keys. You can configure a template sensor in configuration.yaml that maps raw values like power_off to “Off” or localized terms, then reference that sensor on your Lovelace cards.

Q5: Does this solution require third-party proxies or external services?

No. The toolkit runs entirely within your local environment. Artifacts are staged and verified via SHA256 locally, and deployments communicate directly with Home Assistant over the standard local REST API.

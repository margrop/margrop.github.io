To understand why a single platform disruption produces four totally different error codes at the same moment, forget distributed microservices jargon for two minutes and picture Kimi as a packed late-night buffet restaurant.

  • The Front Neon Sign & Paper Menu (www.kimi.com returns 200 OK): You walk up to the door and see bright neon lights and a host handing out blank paper menus. It looks completely open—that's the static CSR browser shell. No actual food has been ordered yet;

  • The Overheated Kitchen Stoves (Partial Outage / 4028 / 504): Orders that reach the kitchen find chefs running on emergency backup stoves. Halfway through stir-frying your code, the breaker trips—leaving your browser spinner spinning forever or spitting out drop code 4028.

Analogy 2: Why Does a Kitchen Power Cut (500) Make the Counter Blame Your Order Slip (400)?

This is the single most frustrating puzzle tonight. Developers keep asking: “I didn’t change a single line of code! Why did a server 500 crash suddenly turn into non-stop 400 Bad Request errors when I clicked Retry?”

  • Step 1 — Mid-Dish Power Cut (500): You ordered a complex dish where the chef first sketches a scratchpad plan (reasoning_content) and calls prep tools. Halfway through plating, the stove trips (500 i/o timeout) and hands back a half-torn receipt;

  • Step 3 — Strict Front-Desk Security Blocks Every Retry (400): Even two minutes later when power returns, hitting Retry sends that torn order slip straight into K3.1 Pro's ultra-strict input validator. The validator immediately rejects it with 400 thinking is enabled but reasoning_content is missing. Because you keep retrying the poisoned history, the 400 loop never heals until you start a clean thread!

1. Control-Plane Bottlenecks Exposed in Kimi's Own 500 Error Reference

Reading the 500 Server Internal Error rows inside Kimi Code’s official documentation (kimi.com/code/docs/kimi-code/error-reference.html) reveals startlingly specific architectural fingerprints:

Figure 12: Verbatim screenshot of Kimi Code’s official Error Reference showing 500 internal strings: failed to connect to … database=membership_, FATAL: terminating connection due to administrator command, failed to evaluate rate limit script, and 未找到该账号 (Account not found).

Every SRE recognizes those exact strings immediately:

  • PostgreSQL Membership DB on the Critical Path: Both failed to connect to ... database=membership_ and FATAL: terminating connection due to administrator command are unmistakable PostgreSQL connection-pool exhaustion / forced backend reset signatures. Because subscription verification, quota tiers, and login resolution all touch membership_ synchronously, a DB wobble simultaneously breaks web login (500 Account not found), triggers 403 unable to verify your membership benefits, and stalls API inference;
  • Redis Lua Rate-Limit Script Contention: Kimi's 5-hour, 7-day, and monthly rolling quota pools execute a server-side Lua evaluation script before dispatching inference. Under retry storms, failed to evaluate rate limit script immediately rejects requests as HTTP 500;
  • Upstream Inference Timeouts & 4028 Drops: Downstream inference workers drop connections with i/o timeout / conn closed / bad connection, non-streaming requests time out at 504 Gateway Time-out after 900 seconds, and internal gateways surface drop code 4028.

2. Why 400 Errors Multiply Right Around Every Outage

Meanwhile, the official 400 documentation and fresh open-source issues expose four rigid validation traps that turn minor hiccups into chronic 400 loops:

  1. Missing reasoning_content After Mid-Stream Drops: Any partial turn cut short by a 500 omits the required reasoning trace; re-sending that thread triggers an instant 400;
  2. Forced Thinking Mode Constraint: K3.1 Pro does not support disabled thinking mode—legacy client toggles attempting to disable reasoning get hard-rejected;
  3. Strict Sampling Temperature Locks: Coding endpoints reject non-standard temperatures (such as Hermes Agent Issue #11765 hitting HTTP 400: invalid temperature: only 0.6 is allowed);
  4. Recursive JSON Schema Rejection: Just yesterday (Nov 19, 2026), zai-org/feedback#1571 confirmed that forwarding tool definitions containing recursive references to api.kimi.ai/coding/v1 causes every prompt—even a plain "hello"—to fail with 400 tools.function.parameters is not a valid moonshot flavored json schema.

3. The Hidden 401 / 403 / 404 Maze: WAF 1010 & Isolated Endpoints

Our live endpoint probes tonight also confirmed two client-side traps disguised as platform outages:

  • Edge WAF 403 error code: 1010: Calling https://api.kimi.ai/coding/v1/messages with a generic Python urllib User-Agent immediately returned HTTP 403 error code: 1010 at the edge before ever reaching Moonshot's application layer, whereas passing a clean custom or curl User-Agent sailed straight through to standard auth validation (401 Invalid Authentication);
  • Strict Three-Account & Two-Region Isolation: Kimi Web Membership, Kimi Code Plans, and Open Platform Pay-As-You-Go balances do NOT share keys, and Mainland endpoints (api.moonshot.cn / api.kimi.com/coding/) are completely isolated from International endpoints (api.moonshot.ai / api.kimi.ai/coding/). Mixing regions or hitting mismatched HTTP paths immediately produces 401 or 404 url.not_found.

7. Five Golden Rules to Survive AI Platform Outages

  1. Bookmark the real status authority: Track status.moonshot.cn (or its JSON API) directly rather than trusting unresolvable status.kimi.com or stale green Instatus mirrors;
  2. Start a fresh thread after any 500 crash: Never hammer Retry inside a session interrupted mid-thinking—otherwise K3.1 Pro's reasoning_content rules lock you into infinite 400 errors;
  3. Keep three wallets and two regions strictly separated: Web Membership, Kimi Code Plan, and Open Platform API keys are non-transferable, and Mainland vs. International endpoints never mix;
  4. Set clean User-Agent headers and strip forced sampling overrides: Avoid generic script UAs hitting Cloudflare/WAF 403 1010 on api.kimi.ai, and avoid passing invalid temperatures or disabled-thinking flags to K3.1 Pro;
  5. Maintain a multi-provider fallback route: Between regulatory compute bottlenecks and control-plane DB/Redis contention, single-vendor dependency is a production liability.

8. FAQ: Seven Sharp Questions Everyone Is Asking Tonight

Q1: Why can my teammate still squeeze messages through while I'm stuck at login or 401/500?

During a Partial Outage, shards fail unevenly. A teammate whose browser still holds a valid, cached session token bypasses overloaded login/membership_ DB paths, whereas any expired cookie or proxy IP shift immediately triggers 401 or 500 validation errors.

Q2: What does error code 4028 mean? Was my account banned or out of credits?

Neither. As observed across Nov 19–20 developer logs and media coverage, 4028 is a server-side internal gateway/inference failure code during capacity crunches. True quota exhaustion returns HTTP 429 (exceeded_current_quota_error or 5-hour usage limit).

Q3: If 500 is Moonshot's fault, why am I also seeing so many 400 Bad Request errors?

Three causes collide: poisoned history missing reasoning_content after a mid-stream 500 drop; rigid K3.1 Pro parameter rules (forbidding disabled thinking and locking temperature); and third-party tool schemas containing recursive references (as documented in zai-org/feedback#1571 on Nov 19).

Q4: When will Kimi Code and Remote Control fully recover tonight?

As of 22:25 CST on Nov 20, 2026, status.moonshot.cn still reports Minor Service Outage with Kimi Code and Remote Control in Partial Outage following tonight's 21:04–21:37 quadruple critical alerts. Intermittent jitter may persist until connection pools and retry queues drain completely.

Q5: Will canceling the $150M Indonesian Blackwell lease cause chronic Kimi outages?

Tightened U.S. BIS remote-compute rules undeniably complicate rapid offshore capacity scaling right as K3.1 Pro coding agents consume surging GPU hours. Expect tighter peak-hour engine_overloaded_error throttling in the near term while domestic compute clusters and scheduling optimizations catch up.

Q6: Is HTTP 403 error code: 1010 an IP ban?

Usually no—it is an edge WAF signature block. In our live probes tonight, default Python urllib User-Agents received 403 error code: 1010 on api.kimi.ai/coding/v1/messages while standard curl and custom headers passed straight through.

Q7: What are the three simplest steps for non-technical web users tonight?

First, check status.moonshot.cn before refreshing endlessly; second, open a brand-new chat thread rather than clicking Regenerate inside a thread that crashed mid-reply; third, temporarily disable misrouted proxies and clear site cookies if SMS/QR login stalls on www.kimi.com.

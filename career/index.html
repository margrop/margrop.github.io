AI-Native Engineering · AI Coding 工程化交付体系

我将 AI Coding 视为需要明确契约、上下文边界与自动化验收门禁的研发流水线，而不是一次性生成代码的聊天工具。人负责问题定义、架构约束、任务拆解与最终把关；Coding Agent 负责在清晰规则下高效实现与补齐验证。

任务拆解 按「数据契约 → 服务端/Provider 逻辑 → 前端交互 → 单元/集成/E2E 测试 → 文档」切分原子任务，逐项提交

真实交付案例：错题本「扫描版 PDF 整份导入与跨页合并」

以 v2026.11.19 版本交付的核心功能（feat: 扫描版 PDF 整份导入为一个识别任务，跨页题目合并并自动摘出答案页答案，单次协同交付 38 个文件）为例：

  1. 需求澄清与边界锁定：解决家长扫描整套试卷 PDF 后必须逐页截图的繁琐操作；硬性要求“识别结果必须先经过批次人工校对才可入库”，且不得破坏既有的单图上传与局部裁剪流程。
  2. 契约与上下文对齐：依据仓库 AGENTS.md 中的 BaseAIProvider 统一接口、withUser 鉴权及中英文 i18n Key 一致性要求，先行定义 ImportBatch 持久化草稿（服务端版本防静默覆盖、条件更新 draft -> started 防重放）、跨页题干衔接规则与答案页自动匹配格式。
  3. 模块拆解与协同编码：拆分为 PDF 页图转换与区域裁剪（scanned-pdf-flow.ts、batch-crop.ts）、多模型 Provider 题目切分扩展（question-split.ts）、批次校对工作台（import-batches/[id]/page.tsx）与双语文案同步。
  4. 测试验收与正式交付：同步交付 4 组 Vitest 单元测试（base-provider.test.ts、question-split.test.ts、scanned-pdf-flow.test.ts、file-import-scanned-pdf.test.tsx）、API 集成测试（import-batches.test.ts）与 Mock AI Playwright E2E（file-import-pdf.spec.ts），人工 Review 并确认 CI 全绿后随 v2026.11.19 自动打包发布至 Docker、桌面端与 NAS 套件。

Observability & Reliability · 稳定性治理与故障恢复

生产系统不仅要能跑通正常路径，更要在部分组件退化、消息重投和流量突发时保持可定位、可降级、可恢复：

  • 四维证据链：把业务数据库（MySQL）、时序指标（Prometheus）、结构化日志（Loki / ELK）与请求 trace_id 串成统一证据链，并通过只读 MCP Bridge 辅助值班排障，不向模型暴露高危写权限。
  • 状态拆解与真实闸门：在观测体系中将 COMPLETED、DENIED（策略正确拦截）、WAITING_APPROVAL 与 FAILED 分开度量，避免用模糊的“总成功率”掩盖安全放行或重试掩盖故障。
  • 后端性能与故障闭环：实践覆盖 P95/P99 尾延迟排查、重试风暴与队列积压治理、Worker 崩溃防双写（Lease + Fencing Token + 幂等唯一约束）、MySQL 在线 DDL 无锁变更以及基于 gperftools 的 JVM 堆外内存排查。

Engineering Principles · 工程原则与研发规范

  • Reliability First（可靠性优先）：先定义身份、权限、超时预算、幂等保护、熔断降级和回滚路径，再扩展功能特性。
  • Security & Least Privilege（安全与最小权限）：凭据隔离于仓库和日志之外，严格参数校验与只读默认边界，高风险副作用必须绑定参数确认。
  • Maintainability & Explicit Contracts（清晰契约与可维护性）：以显式状态机、版本化接口、规范日志与架构约束（如 AGENTS.md）替代隐式约定。
  • Evidence-based Engineering（以证据闭环交付）：无论手工研发还是 AI Coding，交付标准都是可复现测试、覆盖率门禁、可观测指标与故障复盘，而不以“代码生成看起来合理”作为完成依据。
